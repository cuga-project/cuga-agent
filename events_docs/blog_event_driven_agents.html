Agents that wait for the world

CUGA answers when you ask it. With one flag, it also answers when your inbox, your repo, a folder, or the clock changes — and delivers the result back to Slack, Discord, Telegram, or a webhook. Here's the model, and a walkthrough to arm your first standing agent in about fifteen minutes.

A hands-on guide to the event-driven layer for CUGA · EVENTS_ENABLED=1

The default shape of an agent is a turn. You type, it reasons, it calls a few tools, it replies, and then it waits for you again. That's the right shape for a chat box and quietly the wrong one for most of what people actually want automated — because that work doesn't start with a human typing. It starts with the world moving:

When a pull request opens, review it. When this email lands, draft the reply. Every morning at nine, check the Box folder and tell me what changed.

None of those begin with a prompt. They begin with an event, and the agent's job is to have been waiting for it. This is the "ambient agent" idea — a process that runs in the background, wakes on a trigger instead of a message, and surfaces to a human only when it needs a decision. The event-driven layer in CUGA is that capability, built to sit on top of the agent you already run rather than replace it. Flip EVENTS_ENABLED off and CUGA is exactly what it was before; flip it on and the same agent gains triggers, channels, and standing flows.

One envelope, one seam

A Slack message, a GitHub webhook, a polled email, a cron tick, and a file in a folder share nothing at the wire level. The tempting design is a code path per source — and that's how you end up with fourteen slightly different agent invocations and a bug in the thirteenth. CUGA takes the opposite route: every source, however it arrived, is normalized into one envelope and POSTed to one endpoint, /invoke. Learn that shape and the whole runtime is legible.

# the one shape every trigger arrives with, at POST /invoke
{
  "source":  {"type": "channel|integration|time", "name": "gmail", "thread_id": "..."},
  "event":   {"kind": "new_email", "payload": { ... }},
  "text":    "<utterance, if it came from a chat channel>",
  "agent":   "cuga",
  "deliver": true
}

By the time the agent reasons, a Gmail event and a Slack event are the same object, and where the answer goes is read from the envelope's origin — which is why an email-triggered flow can reply into Slack without a single line of code that knows about that pairing. Adding a new source is writing the normalizer that produces this envelope; nothing downstream changes.

The other spine is the trigger registry: one row per (app, event) pair, carrying the trigger definition, payload map, required slots, and the phrases the classifier matches on. GitHub alone exposes fourteen triggers (PR, issue, star, push, release, …); across seven integrations there are 33. Adding one is a single row, and an unknown (app, event) is rejected at build time rather than arming a flow that can never fire.

The agent never sees a token

An event-driven agent acts while you're away, which means it needs standing credentials to your accounts — and that is precisely what you don't want a language model holding in its context, where it can be logged or coaxed out. So the credential boundary is explicit and the agent sits on the far side of it. Tokens live in a separate connections engine; a flow only ever references a credential by a symbolic name:

{{connections['ea::tenant::user::gmail']}}

At fire time that reference is resolved to a real token inside the engine's sandbox, used to poll or receive, and never handed back. The agent gets the email's contents to reason about; it never gets the thing that could read your next thousand emails. If you sketch the sequence, the token's lifetime is a short segment that never touches the box labelled "LLM." That's the invariant worth protecting.

Set it up

The runtime is one command per service. The only irreducibly manual part is external accounts — an LLM key and, for the connectors you want, a bot token or an OAuth app. There are three capability tiers, and you only pay for the infra you use.

TierWhat lights upExtra infra
1 · bareWeb chat · webhooks · direct watchers (Slack / Discord / Box-direct)none
2 · flowsCron / poll + AP-backed triggers (Gmail / GitHub / Box)Activepieces (make ap)
3 · publicSlack events · OAuth consent · Telegrama public URL (make tunnels)

Bare tier — zero extra infrastructure

This is enough to talk to a standing agent over web chat and fire it from a webhook. Clone the repo, then:

uv sync --python 3.12                # CUGA deps → .venv
cp .env.events.example .env          # fill in one LLM key + EVENTS_ENABLED=1

$ cuga start demo --events           # the normal CUGA server, events layer on

On boot it prints a capability report (also at GET /api/events/status) telling you exactly what's live and, for anything that isn't, the one-line fix:

events layer ENABLED — capability report:
  ✓ web chat · webhooks · direct watchers — no extra infra
  ✓ supervisor: ON — sub-agents from supervisor_agents.yaml
  ✗ Activepieces not reachable → cron/poll + AP triggers unavailable (`make ap`)
  ✗ no public URL → Slack / OAuth / Telegram unreachable (`make tunnels`)

Everything runs on CUGA's native port 7860, with or without --events. Open localhost:7860/studio for the console — a deliberately thin UI that only renders backend state.

Flows & public tiers

To arm real triggers you need the connections engine (Activepieces) and, for anything the outside world must reach — Slack events, OAuth callbacks, Telegram — a stable public URL. One wrapper provisions both and then starts the same server:

$ make up            # provisions Activepieces + tunnels, then runs `cuga start demo --events`
$ make public-url     # prints the URL + the exact strings to paste into Slack / OAuth consoles
One tip that saves a lot of grief. Reserve a free ngrok domain and set EVENTS_NGROK_DOMAIN. It pins the public URL so you wire Slack and each OAuth redirect once, instead of re-pointing every console after each restart. Without it you get an ephemeral tunnel that changes every run — and flows that fail opaquely when it rotates.

Arm your first flow, in English

Here's the part that feels like the future. You don't write a flow definition — you describe it. Open the Studio chat (or POST to /api/concierge) and type:

you ▸ when I get an email, draft a reply summarizing my response

A component called the concierge compiles that sentence into a standing flow. It isn't prompt-and-pray: a deterministic pre-router handles high-confidence utterances with no LLM call, a request missing a required slot ("watch which repo?") comes back as a question you answer in the next message, and only genuinely ambiguous input falls through to the model. Every path is validated against the trigger registry before anything arms. The sentence above compiles to:

{ "source": "gmail", "event": "new_email",
  "actions": ["gmail/create_draft_reply"], "outcome": "arm" }

If you haven't connected Gmail yet, the concierge tells you so and hands you the consent link rather than arming a flow that can't fire. Once it's armed, it's a durable thing: send yourself an email and the agent wakes, reads it, drafts the reply, and — because Gmail is a polling trigger — does it on the connector's next poll. Want to act, not just watch? The same grammar chains actions:

you ▸ when I get an email, email me a summary AND reply to the sender

That compiles to a validated two-action chain. Anything destructive routes through an approval step before it executes — the guardrail ships before the sharp actions do, not after.

You can force a mode explicitly when you don't want to leave it to the classifier:

you ▸ /watch    # push/webhook triggers
you ▸ /schedule every weekday at 9am, summarize new files in my Box folder
you ▸ /poll     # polling triggers    /cron  /push  — all outrank the classifier

How a message routes

Web, Slack, Discord, and Telegram all apply the same rule, in order, so behaviour is identical on every surface:

  1. A slash command (/automate, /watch, /schedule, /cron, /poll, /push) goes straight to the concierge — it outranks even an armed channel watcher.
  2. An utterance the classifier reads as standing intent (cron/poll/push phrasing) takes the NL→Flow path.
  3. A thread with an open concierge question stays with the concierge, so slot-filling works across messages.
  4. Everything else — plain conversation — goes straight to the agent, no concierge hop.

On Slack and Discord a mention gate runs first (EVENTS_SLACK_CHAT=mention): only @-mentions, DMs, and replies to the bot reach chat, while armed channel watchers still see everything. It's the difference between an agent that's present in a busy channel and one that's noisy in it.

Bring your own agents

Nothing above is tied to a specific agent. There's exactly one addressable agent, cuga; with EVENTS_SUPERVISOR=1 it becomes a supervisor that fans out to a roster of specialists and lets the answer bubble back up. The roster is a YAML file, and it's yours to replace:

EVENTS_SUPERVISOR=1 \
EVENTS_SUPERVISOR_ROSTER=/path/to/my_agents.yaml \
  cuga start demo --events

A specialist is a skill, not a deployment — a name, a prompt, its tools, and the triggers it handles:

- name: invoice_checker
  special_instructions: |
    You verify invoices: amounts, due dates, duplicate detection. Be terse and factual.
    HANDLES TRIGGERS: gmail/new_attachment (An email with an attachment)
  mcp_servers:
    - name: cuga-text

Append the block, run make reload, and the supervisor routes matching events to it. The HANDLES line names app/event pairs from the registry verbatim — and an offline gate fails the build if a specialist claims a trigger that doesn't exist, or a registry trigger is claimed by nobody. Channels and credentials stay at the platform level; a sub-agent gets event content and the tools you scoped it to, never a token and never a channel of its own.

Where this goes

If the last stretch of agent building was about making the single turn good — better tool use, better planning inside one request — the next one looks like making the agent a standing participant in systems that already exist. Not a chat box you visit, but a quiet process wired into your repo, your inbox, your queue, that mostly does its job and occasionally asks you a question. The pieces that make that trustworthy are unglamorous and durable: a normalized event envelope, a credential boundary the model sits outside of, a compiler from plain intent to a validated standing flow, and an approval gate in front of anything that writes. Prompts change every few months; those don't.

The nice part is that you don't start over to get there. It's one flag on the agent you already run. Clone cuga-agent, cuga start demo --events, and describe the first thing you'd like it to wait for.

Architecture, per-connector setup guides, decision records, and an honest known-gaps list live under events_docs/ in the repo. The events layer is additive and behind EVENTS_ENABLED — base CUGA is unchanged when it's off.
