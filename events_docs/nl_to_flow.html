NL→Flow

How one English sentence becomes a standing, armed flow — and why it can't silently become the wrong one.

The contract: an utterance either resolves to exactly the right flow, or to a question — never silently to the wrong flow. Everything below exists to enforce that sentence.

The shape: the LLM proposes, the registry disposes, Activepieces executes

There are exactly two fuzzy hops in the whole pipeline — everything else is deterministic code that can be unit-tested, replayed, and benchmarked:

HopWhat decidesGuarded by
Slash commands (/automate /push /cron /poll) deterministic router — the LLM never sees the mode—
Pre-router (events/flowspec.py) deterministic: classifier + slot extraction + confidence rules the 47-case benchmark, gated on zero wrong-at-high
Fuzzy hop #1 — intent the concierge LLM, for utterances the pre-router won't claim the registry validation gate disposes of every proposal before anything is built
Arming (connect gate → dedup → build) deterministic — one path, both doorsthe offline API-contract suite
Fuzzy hop #2 — payload maps curated {{trigger.…}} field maps per trigger _raw safety net + tests pinning known AP piece bugs

The walkthrough — one real sentence

1
You say "when a PR is opened, review it and summarize the risk" — from any channel. The origin thread (gw:slack:C… / web) is remembered: answers go where you asked from.
2
The pre-router resolves. Kind = PUSH (an explicit standing-flow marker — when / whenever / every time / as soon as — is required; a loose match like "summarize the open PRs" is refused). The registry's own phrases match the trigger: github/new_pr. Slot extraction finds no repo.
3
Confidence is judged honestly. high demands: a standing-flow marker, one distinct app among the phrase hits, and no other app's vocabulary in the sentence ("…my repo or my inbox…" is refused even when only one app's phrases matched). Anything less is ambiguous and goes to the LLM — declining to be confident is always safe; being confidently wrong never is.
4
The registry gate disposes. triggers.validate("github", "new_pr", {}) → the required repo slot is missing. Nothing is built. You get back exactly one question: "Which repository (owner/repo) should I watch?" — and the partial spec is parked on this conversation thread (10-minute TTL).
5
Ask-till-legit. Your next message — "acme/api" — is first tried as the answer. A bare token must fit the slot's shape (owner/repo for repo, digits for a Box folder, a quoted string for a Gmail label). A reply that reads as a new request ("actually, what's the weather?") is never crammed into the slot — the parked spec is dropped and the message routes normally. You are never trapped in a prompt.
6
Both doors arm through the same tool. The pre-router calls the very find_or_create_flow the LLM would call — so the connect gate (is GitHub connected? only the source app is checked), dedup (same agent + trigger + config + sink ⇒ REUSING, refereed by a DB unique index), and the flow build are one code path, not two.
7
The flow is real — and it targets THE one agent. An Activepieces flow named push-github-new-pr-cuga: the piece trigger bound to your connection (AP holds the token — the agent never sees it), one HTTP step POSTing the envelope {agent: "cuga", source, event} back to CUGA's /invoke. No specialist is named at arm time — the concierge compiles the trigger, never picks an agent. Publishing registers a real repo webhook.
8
Forever after: PR opens → webhook → AP resolves the curated payload map ({{trigger.pull_request.title}}…, with _raw as the safety net) → /invoke {agent: "cuga"} → the supervisor picks the right specialist from its roster (supervisor_agents.yaml) per wake-up, the sub-agent runs, and the answer bubbles up to the channel you armed it from. (With EVENTS_SUPERVISOR unset, the plain classic CUGA agent answers directly.)

The confidence ladder

ConfidenceMeaningWhat happens
highone app, registry-validated, marker present armed deterministically (no LLM call — instant), or its ONE missing-slot question

How we know it works — the benchmark

tests/events/test_flowspec_bench.py: 47 hand-labelled cases (utterance → expected FlowSpec) run in CI on every change. The gates, strongest first:

  • Zero wrong-at-high zero tolerance — a high-confidence resolution that disagrees with the label is a user silently arming the wrong watcher. On its first run this gate caught two real bugs before any user could.
  • Every push trigger has a proven happy path — canonical phrasing must fast-path, for all triggers in the registry (a new trigger without bench cases fails the build).
  • Asks fire when a required slot is missing — never a guess; and slot values extract verbatim (a mangled slot is a garbage AP trigger).

Current scorecard: fast-path 35/37 push cases (94%) · correct-at-high 35/35 (100%). The ask-till-legit loop is unit-tested (park → fill → arm; topic-change → drop) and proven live.

What's deliberately NOT the LLM's job

  • Validation — the gate exists to catch the LLM's hallucinations; an LLM validating its own proposal is the fox auditing the henhouse.
  • The sink — "answers go where you asked from" is a fact we already hold, not a judgment (an explicit "email me instead" overrides it, and that part IS the LLM's).
  • The connect gate — whether a credential exists is a database fact behind a security boundary.
  • Dedup — identity under concurrency belongs to a canonical key + a DB unique constraint, not to sampling.

What's next (roadmap P3)

The LLM seam scored by the same benchmark — the concierge emitting a structured FlowSpec whose JSON schema is generated from the registry (a hallucinated trigger becomes a schema violation, not an armed flow) — then a model bake-off (accuracy / latency / cost). See ROADMAP.md.
