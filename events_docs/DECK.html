Channels & Events: where we are

Two features, delivered as a second service beside CUGA — never bolted into it. Channels let people talk to CUGA from Slack, Discord, Telegram or the web. Events let them ask CUGA to keep doing something — on a schedule, on a change, or on an inbound webhook — with a human approving the exact prompt before anything is armed.

Both go through one door. Every message from every channel lands on CUGA's POST /run, and CUGA — not the eventing service — decides whether this one is ordinary chat or an attempt to arm something. That inversion is the change that matters most here.

The two features

Channels first, then events on top

They are deliberately separate. Channels is a transport question — how a message reaches the agent and how the answer gets back. Events is a time question — what happens when nobody is in the room.

CUGA owns the front door for both. Slack, Discord, Telegram and the web all land on CUGA's /run. The channel adapters hold the bot tokens because they own the sockets, but they make no routing decision. The eventing service is invoked only when the utterance is actually about eventing — so ordinary chat stays exactly as fast and as simple as it was before any of this existed.

① Channels — talk to CUGA from anywhere

Four surfaces, all live: web, Slack, Discord, Telegram. Slack and Discord require an @mention to engage; once the bot roots a thread, follow-ups in that thread need no re-mention. Replies go back to the thread they came from.

② Events — make it keep happening

A plain chat stays plain chat. Only /automate, /watch, /schedule reach the eventing layer. It arms a cron, a poll (fire only on change) or an inbound webhook — then fires on its own and delivers back through whichever channel you came from.

The one rule, applied in one place

slash verb (/automate /watch /schedule /cron /poll /push /cancel)   → eventing
this thread already has an arming dialogue open ("yes", "change …") → eventing
everything else                                                     → the agent

That second line is what makes the back-and-forth work. A bare yes means nothing on its own, so CUGA remembers which threads are mid-dialogue — from the state the eventing service returns — and keeps routing them until it says armed or cancelled. It is a routing hint, not state: the eventing service holds the real parked entry and is the only thing that can arm.

The next section traces both branches of that rule hop by hop, from the same Slack channel.

The round trip, concretely

1 · in
You @bot /automate every minute send me the price of bitcoin in Slack.
2 · to CUGA
The Slack adapter POSTs CUGA's /run. It holds the token; it decides nothing.
3 · CUGA decides
Slash verb → forward to the eventing service. (Plain chat would stop here and answer.)
4 · confirm
A card comes back in that thread: the exact prompt, the cadence, the delivery target. Nothing armed yet.
5 · yes
Replied in-thread, no re-mention. CUGA sees the open dialogue, forwards it, the flow arms deterministically.
6 · fire
The scheduler wakes it and POSTs /invoke. Each fire runs on a fresh thread so tick #288 doesn't drag 287 prior turns.
7 · execute
/invoke → CUGA /run → the supervisor picks pricebot → cuga-finance.
8 · back
Delivered into the original Slack thread. Execution thread ≠ delivery thread.

Same channel, one word apart

Two messages from Slack, traced hop by hop

This is the clearest way to see what the door actually buys. Both messages are typed into the same Slack channel, both hit the same receiver, both travel the same first four hops. The only difference is one word — and the only place that word changes anything is inside CUGA.

Without /automate — ordinary chat

@cuga-app what is IBM trading at?
  1. Slack delivers an app_mention event to the events service: POST /api/events/slack/events. The receiver lives here because it owns the signing secret and the bot token.
  2. Signature verified · <@Uxxx> stripped · deduped on ts · acked in <3 s, real work handed to a background task (Slack's timeout is unforgiving).
  3. cuga_door.ask(...) → POST cuga-core/run with thread_id = gw:slack:C123#1712…. The adapter does not look at the text.
  4. The door decides. No slash verb; this thread has no open dialogue → _forwards_to_events() returns False. The eventing service is never called.
  5. The supervisor runs, picks a sub-agent, calls cuga-finance over MCP.
  6. /run returns {"answer": "IBM is trading at …"}.
  7. The adapter posts it back into the thread with chat.postMessage.
Eventing's total involvement: it carried the message and carried the answer back. The concierge, the scheduler and the store were never touched. Nothing was persisted. Identical latency to CUGA with no eventing service deployed at all.

With /automate — arming a flow

@cuga-app /automate every morning at 9 tell me IBM's price
  1. Same receiver, same endpoint. byte-identical
  2. Same verification, same dedup, same 3-second ack. byte-identical
  3. Same cuga_door.ask(...) → same POST cuga-core/run. byte-identical
  4. The door decides. _SLASH_VERBS matches (a leading @mention is tolerated) → forward. The agent is never invoked, so it never tries to implement the schedule.
  5. POST events/api/concierge — the text, the thread_id, the channel envelope, plus the gateway token and the identity headers so the flow arms in the scope your Studio browses.
  6. Concierge parses to DRAFT, strips the cadence out of the prompt ("every morning at 9 tell me IBM's price" → "Tell me IBM's price."), returns state: "confirm" + a card.
  7. CUGA notes the thread in _events_open_threads and returns the card as the answer, tagged routed_to: "events". The adapter posts it into the thread. Nothing is armed.
  8. You reply yes in-thread — no re-mention. Hops 1–3 repeat identically; at hop 4 there is still no slash verb, but the thread is open, so it forwards. The concierge arms deterministically, returns armed, and CUGA drops the thread from the open set.
  9. 09:00 the next day: the scheduler fires → /invoke → a fresh /run → the answer is delivered into the original Slack thread.
The word /automate changes exactly one branch, in exactly one file. Everything upstream and downstream of that branch is the same code.

Telegram, Discord and the web Studio follow exactly the same two lanes — different adapter, same cuga_door.ask(), same door, same rule. Web chat goes through /stream instead of /run, and the rule is applied there too: an arming reply comes back as a single SSE Answer frame.

Why this ordering matters. It used to run the other way — every channel message went to the eventing layer first, which decided chat-vs-arming and only then called CUGA. That made eventing the front door for ordinary chat, so chat inherited the availability of a feature it does not use. Now the exception asks permission from the rule, not the other way round.

NL → Flow

Nothing arms until you approve the prompt

The risky part of "turn this sentence into a standing job" is not the schedule — it is the prompt the agent is handed on every single fire, forever, with nobody watching. So a human goes in front of it.

  1. DRAFT — the utterance is parsed into cadence + prompt + delivery target. The scaffolding is stripped: "every 5 mins check ibm stock price" → "Check ibm stock price." The schedule already handles recurrence; leaving it in the prompt asks the agent to implement a loop.
  2. NEEDS_INPUT — if something required is missing (no cadence, no push source) it asks, through the same channel you came from, and waits.
  3. CONFIRM — you see the card. Arm it · Edit prompt · Cancel.
  4. ARMED — and only then. Cron and poll arm deterministically from the approved text; there is no second LLM pass free to arm something you never read.

Drafts expire after 10 minutes. Plain chat never enters this dialogue at all.

Deployment

Two services, one image

cuga-core — vanilla CUGA

The agent, the graph, the Studio UI, /stream, /run. Imports nothing from the events package. No scheduler, no channel loops, no bot tokens.

cuga-events-svc — the eventing service

Triggers, the native scheduler, the four channel adapters, the concierge, /invoke. Arms flows and fires them; executes by calling CUGA's /run. A singleton — the scheduler and channel loops are process-wide.

"Combined" mode — events mounted onto CUGA's FastAPI app — has been removed entirely, along with the two in-process runtimes it needed. There is one topology.

CUGA runs perfectly well without any of this

ScenarioWhat happens
Eventing never deployed (EVENTS_API_URL unset)Forward disabled. /run and /stream behave exactly as upstream CUGA — a slash verb is just text.
Eventing deployed but downChat unaffected (it never calls out). Arming returns an honest sentence naming the unreachable URL. No stack trace, no hang.
Eventing turned offSame as never deployed — unset one variable.

The coupling is one variable, one direction: CUGA imports nothing from cuga.backend.events (a test fails if that regresses), and the only link out is an HTTP POST guarded by EVENTS_API_URL. The dependency runs the other way — the eventing service needs CUGA, because CUGA executes every agent call.

Why one image and not two? The events package now imports exactly one thing from CUGA core (resolve_secret), so a lean events image is genuinely feasible. It is not worth it yet: one image means one build, one tag, and no version-skew risk across the /run contract. Worth revisiting when the two deploy on different cadences.

Activepieces

Wired in, switched off — and why we still care

What works without it

Everything above: all four chat channels, cron, poll, inbound webhooks, and the direct watchers for Slack, Discord and Box. The native scheduler runs cron/poll in-process. No extra infra.

What it unlocks when you turn it on

Push triggers on SaaS you don't own — Gmail new-email, GitHub repo events, Box new-file, Calendar. AP holds the OAuth tokens (encrypted; the agent never sees them) and does the provider-specific webhook plumbing we would otherwise write ~30 times.

Why it's off: it is a whole extra service, and every path that doesn't need it should not depend on it. AP is one trigger backend, not the spine. The harness proves it: with AP down, the only failures are the two assertions that exist to check AP is down.

Heads up for the day you enable it: we fixed a latent crash in the AP engine — reachable() had been pasted into the middle of __init__, so half the constructor never ran. It fails on the first AP call with 'APEngine' object has no attribute '_auth_lock'. Invisible while AP is off.

Slack's Request URL points at the EVENTING SERVICE, never at CUGA. "CUGA is the door" describes where the decision happens — one hop later, invisible to Slack. The receiver did not move. Pointing Slack at cuga-core gets a 405 for that path and Slack reports "your request URL returned an HTTP error". Use cuga-events-svc. Also: only one process at a time may serve a given Slack app or long-poll a given Telegram bot — local plus CE on the same bot gives 409 Conflict.

Opening that Request URL in a browser also used to answer 405 — a GET on a POST-only endpoint, correct but alarming, and indistinguishable from having the wrong host. It now returns a short JSON saying the endpoint is healthy, that Slack delivers by POST, and which host is the right one. To exercise it for real:

curl -X POST <request-url> -H 'Content-Type: application/json' \
     -d '{"type":"url_verification","challenge":"probe"}'      # prints: probe
