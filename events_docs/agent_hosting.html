How agents are hosted

The classic CUGA FastAPI server vs the events world — told from the agent's perspective, because that's where the confusion lives.

Old world — “I am the server”

                     ONE SERVER = ONE AGENT ("cuga-default")

  user (chat UI) ──► /stream ─────────────► DynamicAgentGraph  ◄── built ONCE at startup,
                     (no agent parameter —        │                lives in app_state
                      there is only me)           │
                                    ┌─────────────┴─────────────┐
                                    │  my internal ROLES        │   not addressable,
                                    │  · task analyzer          │   not registrable —
                                    │  · plan controller        │   just how I think
                                    │  · API planner / coder    │
                                    │  · browser / QA / answer  │
                                    │  · CugaLite fast path     │
                                    └─────────────┬─────────────┘
                                                  │ (optional, YAML at startup)
                                        SupervisorNode
                                        ├── CugaAgent "crm"      ─┐ my hidden committee:
                                        ├── CugaAgent "email"     │ callers never see them,
                                        └── A2A ► remote agent   ─┘ I delegate internally

     want a second top-level agent?  →  run a second server,
                                         or embed CugaAgent() in your own app (cuga-apps)
“Every request that reaches this process is for me. My name is hardcoded (cuga-default). My skills are the server's config. If I have sub-agents, they're my private staff — nobody outside can address them.”

Events world — “I'm a resident, not the building”

                  ONE SERVER = ONE SHARED STACK + A FLEET

   web chat ──┐
   Slack ─────┤   ┌── /api/concierge ── pre-router / LLM ──► arms flows, routes questions
   Discord ───┼──►│
   Telegram ──┘   └── /invoke {agent, source, event}   ◄── EVERY wake-up call, one envelope
                          ▲                ▲
   AP flows (github,      │                │         /hook/{name}?route=1
   gmail, box, cron…) ────┘   direct       │               ▲
                              watchers ────┘         external systems
                              (slack/discord/box)
                          │
                          ▼  "wake agent X"  (by name, validated, scoped)
              ┌───────── CugaRuntime — builds my graph on first call, caches it ─────────┐
              │                                                                          │
   AgentStore │   pr_reviewer   mailbot   incident_triage   travel_planner   … 27+      │
   (sqlite,   │       │            │             │               │                       │
   runtime-   │       ▼            ▼             ▼               ▼                       │
   editable)  │   my OWN DynamicAgentGraph — my prompt, my MCP tools, my channels,       │
              │   my declared triggers, my access list  (internals = the old picture)    │
              └──────────────────────────┬───────────────────────────────────────────────┘
                                         ▼
                SHARED app_state: one policy system · one model config
                one tool registry · one tracing pipeline · (credentials live in AP)
“I'm a row in the AgentStore — a spec: prompt, tools, channels, triggers, who may use me. I don't own the process; I get woken by name through /invoke when a channel message routes to me, a trigger I declared fires, or a webhook names me. My graph is built lazily and cached. I share the house — policies, model, tracing — with 26 housemates, but my skill, my watchers, and my permissions are mine.”

Side by side

Classic serverEvents world
Identitythe deployment (cuga-default, fixed at startup) data — a registry row, upserted live (Studio / API / seed.py)
Addressabilityone front door (/stream); sub-agents invisible every agent reachable by name via /invoke, or picked by the concierge
Multi-agentsupervisor mode: a YAML committee behind the one agent a fleet beside each other, individually routable + watchable
What wakes an agenta human typing humans, schedules, polls, webhooks, and 33 integration triggers
Per-agent surfacetools (via the one config) prompt · tools · channels · trigger declarations · access roles
Cost of agent #28a new server (or an SDK app) one registry row; the graph is built on first use over the shared stack
The one-line delta: in the old world the agent is the deployment — identity fixed at startup, one front door, sub-agents private. In the events world the agent is data — identity is a registry row, the /invoke seam wakes anyone by name, and the expensive stack is built once and shared by all.

Where each shape still wins

  • Classic + supervisor — one composed skill with a hidden committee (the cuga-apps/ouroboros shape). One door is the feature.
  • SDK (CugaAgent()) — embedding CUGA inside your program, no server at all.
  • Events fleet — anything triggers and channels touch: a GitHub webhook must wake pr_reviewer by name, not ask a committee to guess. They compose — a fleet member could itself run supervisor-enabled if a use case ever wants a committee behind one resident.
