Event-Driven CUGA — v1 Roadmap

A Google-Apps-style suite of event-driven agents: talk to them from any channel; they watch your tools and act — automatically, safely, in your words.

Scope frozen · target: 4 weeks to ship + blog. The mechanism is built; the work left is breadth, vetting, and a demo — not new architecture.

DEFINITION OF DONE — v1

We ship when: 4 channels let a person converse with the agents · a core of 6 integrations both watch and act, proven by a two-level benchmark (NL→AP and execution) · 5 flagship agents pass a per-agent vetting checklist · the suite is deployed (HuggingFace) with a blog + demo video. Stretch adds (Outlook, an HTTP "any-API" action, LinkedIn/X) land if the core is green first. Anything past this is v2.

Scope 4 — Benchmarking (two levels) — "armed ≠ works"

The core discipline of v1. Arming a flow is not proof it works. We benchmark at two levels — and a capability isn't "done" until it passes both.

LEVEL 1 · NL → AP

Did we build the right flow?

  • Runs offline against a fake engine — fast, deterministic, every commit (CI).
  • Scores mode · trigger · action · gate-outcome, and CORRECT-AT-ARM (armed flows that were right).
  • ✓ exists — 22 cases at 100%. Grow it as integrations land.
LEVEL 2 · EXECUTION

Does the flow actually work?

  • Runs against real Activepieces + real connections — nightly / pre-release.
  • Per (trigger, action): arm → valid+enabled → fire (synthetic or a real controllable event) → right step ran (AP run SUCCEEDED) → effect verified in the target app → answer delivered.
  • Metrics: FIRE-RATE · EXECUTION-CORRECT · EFFECT-VERIFIED · DELIVERY-OK.
  • ◐ fragments only — validity gate + --check + github synth fire exist; the harness that asserts the effect is the Week-2/3 build.

Fire strategy per trigger (already tagged in the registry): synth = machine-fireable (github webhooks) · real = a controllable local action (box upload, a slack message) · manual = needs a real external event (a real email) — those get a scripted send in the harness. This is exactly what turns the 5 agents' per-agent checklist from "armed" into "proven."

The 4-week plan

Week 1 — Freeze & harden the core

Stop adding mechanism. Make what exists provably solid.

  • Fix the direct-executor AP run-level error (or formally scope v1 to AP-push actions and document it).
  • Prove Telegram return-to-caller; hardening pass on the 4 channels.
  • Live-vet Gmail actions end-to-end (real email → real draft/reply/send).
  • Lock the credential/security story (AP owns tokens; vault the AP password).
Exit: zero open bugs in the core arm→run→deliver loop; Gmail agent demoable live.

Week 2 — Breadth: the "act" half

Turn 1 acting integration into 6. Pure registry data + vetting — no new engine.

  • Add + --check + live-vet actions: GitHub (issue/comment), Slack (post), Calendar (create-event), Sheets (append-row); Box upload if cheap.
  • Add the Calendar and Sheets triggers + OAuth entries.
  • Each new action: one board example + one gate test + a Level-1 benchmark case (CORRECT-AT-ARM 100%).
  • Build the Level-2 execution harness (arm → fire → assert the right step ran → verify the effect).
Exit: 6 integrations watch and act, each passing Level-2 (a real fire + a verified effect).

Week 3 — Build & vet the 5 agents

Assemble the product and prove each one truly works.

  • Configure the 5 flagship agents as saved, shareable event-driven apps.
  • Per-agent vetting = the Level-2 harness run end-to-end: arm → fire a real event → right action ran → effect verified → answer delivered.
  • Fix whatever Level-2 surfaces. No new agents beyond the five.
Exit: a green vetting checklist for all 5 agents — screenshots + logs as receipts.

Week 4 — Ship & tell the story

Deploy, polish, publish.

  • Deploy the suite to HuggingFace Spaces (or equivalent); smoke-test in the hosted env.
  • Final security + error-handling pass; freshen the generated docs (deck, API spec, checklist).
  • Write the blog + record a demo video of each agent. Squash + open the PR.
Exit: live URL + published blog + merged PR. v1 is done.

Explicitly out of scope (v2)

  • WhatsApp, Outlook/Teams, Twilio channels
  • Salesforce / HubSpot / Jira / Notion
  • Generic "any REST API" as an action (HTTP-out)
  • Nested branches & numeric branch conditions
  • Tool-first actions (agent holds its own tool)
  • Gmail archive/label/delete (custom_api_call)
  • Run-time approval for destructive actions
  • Multi-tenant load & executor cleanup

These are good — just not what makes v1 shippable. Naming them is how we stop chasing.

What "truly working" means (the vetting bar)

A capability counts as done only when: it arms via natural language from a channel · the flow is valid in Activepieces · a real event fires it · the right action executes (verified in the target app) · the answer returns to the origin channel · and there's a test + a benchmark case guarding it. "Armed" ≠ "works" — the whole v1 is about closing that gap for a curated set.
