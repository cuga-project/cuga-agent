The whole thing in one line

Every trigger — a chat message, a scheduler tick, an inbound webhook — is normalized into one envelope and POSTed to one internal seam, POST /invoke. The seam runs either the concierge (the router) or a concrete agent, then delivers the answer back to wherever the trigger came from. Adding a channel or a trigger never touches the agent, delivery, or the Studio — they all sit behind that contract.

# the universal lifecycle — identical for chat, cron, poll, webhook
trigger  ─▶  normalize to Envelope  ─▶  POST /invoke  (X-Gateway-Token)
             ─▶  auth · validate · resolve scope · expiry · account-link · poll-augment
             ─▶  fork on envelope.agent:
                    "concierge" ─▶ concierge.run()  { slash · pre-route · NOW→agent · LLM-router }
                    concrete id ─▶ runtime.run(agent)
             ─▶  runtime.run("cuga") ─▶ DynamicAgentGraph via AgentLoop ─▶ answer
             ─▶  metadata footer · poll-delta gate · deliver back over the origin transport

The moving parts

One FastAPI process (the same CUGA server, with EVENTS_ENABLED=1). The events layer mounts its whole surface onto it via register_events_routes(app, …); when the flag is off, none of this exists and CUGA is unchanged.

No Activepieces anywhere in this runbook. Everything here runs on the native/direct path: direct channel backends + the in-process scheduler + inbound webhooks. AP is a separate connector backend for SaaS push triggers (Gmail/GitHub/Box…) — deliberately out of scope here. Where a feature has an AP variant, it is only named, never detailed.

How to read this

  • Sequence diagrams are numbered step lists: each step names the two endpoints (A ──▶ B), the exact API call, and what happens.
  • Data envelopes are shown as real JSON with the fields that matter highlighted. Values like <chat_id> are placeholders.
  • Every doc ends with a Sources footer naming the exact code files it was written from. If you change one of those files, update that doc — that is the whole anti-drift contract.
Maintenance / anti-drift. These files are hand-authored, not generated. They are kept honest by the Sources footer on each page: it lists the code files that page describes. The single rule — change a source file → update the page that cites it. The pages that pin the most volatile facts: API Reference (routes & response shapes), Channels (envelope construction & thread_id formats), and Scheduler (the SQLite columns).
