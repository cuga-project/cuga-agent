The scheduler & polling infra

Recurring triggers with no external scheduler: an in-process loop over a SQLite next_fire column, a built-in cron parser, and a stateful poll-delta gate that only speaks up when something actually changed.

The loop — one in-process task

When EVENTS_SCHEDULER != "ap" (the default native), a coroutine is launched at boot into app.state.events_background. It is a plain asyncio loop — no external cron, no Celery, no AP. It wakes every 10 s, fires everything due, and sleeps.

# native_scheduler.py — run_scheduler(store, *, port, token, tick=10.0)
while not stopped:
    await process_due(store, time.time(), _fire)     # fire everything due right now
    sleep(tick)                                       # 10s, in 1s slices so stop is prompt
This loop is the launcher's job. It only runs if the boot code actually launches app.state.events_background — the same background list that starts the Telegram long-poll and Discord Gateway. If those channels are silent, the scheduler is too: check the boot log for events: launched N background task(s).

process_due — fire, reschedule, retire

process_due(store, now, fire_fn) · native_scheduler.py
1
select due
store.due(now) → SELECT * WHERE backend='native' AND status='active' AND next_fire > 0 AND next_fire <= now ORDER BY next_fire
AP-backed rows are fired by Activepieces, never this loop — the query filters them out.
2
expiry check
if sub.expires_at and now > sub.expires_at → store.delete(sub.id); skip
A bounded flow past its deadline is retired before running.
3
fire
await fire_fn(sub) # POSTs a tick envelope to /invoke (below); bare-except so one bad fire can't stall the loop
Exactly once per due row — a row an hour overdue fires once, not 30× (lazy catch-up).
4
reschedule or retire
nxt = next_fire_after(sub, now); if not nxt or (expires_at and nxt > expires_at) → delete; else mark_fired(next_fire=nxt, fire_count+1)
next_fire_after: interval → now + interval_seconds (lazy); cron → next_cron(expr, now); neither → 0 (stop).

The cron parser

next_cron(expr, after) returns the next epoch strictly after after matching a 5-field expression minute hour day-of-month month day-of-week, scanning minute-by-minute up to ~366 days. Each field supports *, a, a-b, a,b,c, */n, a-b/n; day-of-week is 0=Sun…6=Sat with 7==0.

How a tick reaches the agent

The fire_fn POSTs a time-source envelope to the same /invoke seam every other trigger uses — with deliver:true, so CUGA delivers the answer itself (no AP send step).

# native_scheduler.py — _invoke_body(sub) → POST http://127.0.0.1:<port>/invoke  (X-Gateway-Token)
{ "text": sub.prompt,                         # the one-run task (cadence already stripped)
  "agent": sub.target_agent,                 # "cuga"
  "deliver": true,                          # CUGA-owned delivery over the origin transport
  "source": { "type": "time", "name": "poll", "thread_id": "gw:telegram:111222333" },
  "event": { "kind": "tick", "payload": {} },
  "subscription_id": "cuga-8ab9cf", "expires_at": null }
// /invoke decodes gw:<channel>:<native> from thread_id and delivers via delivery.send_direct.
// A non-message fire is labelled "⚡ flow fired · cron tick · <flow_name>" and logged to the Runs table.

State — the subscription table

All of this lives in one database — PostgreSQL in every real deployment and in local dev (make pg); SQLite only for the hermetic offline suite. The native scheduler reads and writes these columns; the AP columns (ap_flow_id) stay empty on the no-AP path.

Stateful poll — report only on change

A POLL is a cron that decides whether to speak. The gate lives entirely inside /invoke (there is no /api/events/poll route) and leans on a per-subscription watch_state row. Four tiers:

Tierwatch_state.kindFires whenStores
0(no row) alwaysevery tick (a plain cron report)nothing
1thresholdabs(new−baseline)/abs(baseline) ≥ threshold (e.g. a 5% move)a baseline scalar; first tick seeds it, never alerts
1identityany new key vs a seen-set (new items, dedup by key)keys only, capped at 5000 — scales to millions of items
2fuzzythe agent itself judges "materially changed"a compact state string fed back next tick

The <<SIGNAL>> protocol

On each POLL tick, /invoke appends a [WATCH] instruction (augment_prompt) telling the agent to end its answer with one machine-readable line. The gate parses it, decides, and strips it from the human reply.

# the agent's final line, by tier
threshold  →  "<<SIGNAL {\"value\": 63799}>>"
identity   →  "<<SIGNAL {\"keys\": [\"paper-2401.001\", \"paper-2401.002\"]}>>"
fuzzy      →  "<<SIGNAL {\"changed\": true, \"state\": \"rain now forecast for 3pm\"}>>"

# inside /invoke — poll_state, pure decision, no I/O
_clean, _signal = poll_state.parse_signal(answer)     # split human text ⟂ signal
_dec = poll_state.decide(watch_state, _signal, now)   # → Decision(changed, state, reason)
store.set_watch_state(_dec.state)                      # persist baseline / seen-keys / fuzzy-state
if env.deliver and _dec.changed:  deliver(_clean)     # else: suppress, log status="nochange"

The delta spec is seeded at arm time by poll_state.extract_spec(utterance) (LLM-first, EVENTS_POLL_LLM=1, regex fallback) → spec_to_state. The watch_state row: subscription_id, kind, seen_keys, baseline, reset_policy, value_path, threshold, updated_at.

Bounded runs

"… for one hour" sets expires_at on the subscription. It is enforced in two places, both lazily: process_due deletes a due row already past the deadline before firing, and /invoke deletes the subscription and returns {expired:true} instead of running the agent. See NL→Flow §bounded.

Scaling notes (honest)

  • Single owner. The loop is one asyncio task per process. Run one instance (min = max = 1) — N replicas each fire every due row → duplicate deliveries.
  • Ephemeral state. events.db is SQLite on local disk. On a stateless deploy it resets on restart (armed flows + watch-state lost). Durable multi-replica scheduling means externalizing state (Postgres) and electing a single scheduler — future work.
  • Fingerprint, not content. The identity tier stores keys, not items — "did anything new appear" over a million-file folder is a set membership check, not a diff.
