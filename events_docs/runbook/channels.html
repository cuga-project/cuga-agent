Channels — message in, answer out

How a human message reaches CUGA and how the reply gets back, for every channel — the transport, the filter, and the exact data envelope. All four are direct (no Activepieces).

Overview Channels /invoke & Concierge NL→Flow Scheduler & Polling API Reference Agents Examples

The one rule that makes all four the same

All four channels do the identical thing: normalize their native message and hand it to CUGA's POST /run via cuga_door.ask() — then take the returned answer and send it back over their own transport. The adapter makes no routing decision at all. CUGA decides whether the utterance is ordinary chat or an attempt to arm something; only in the second case does the eventing service's concierge get involved.

This is an inversion of the earlier design, in which each adapter POSTed /invoke with agent:"concierge" and the eventing layer decided chat-vs-arming. That made eventing the front door for ordinary chat, so chat inherited the availability of a feature it does not use. Web previously called concierge.run(…) in-process; it now goes through /stream, which applies the same rule.

The one distinction that decides "needs a public URL": an outbound transport (Telegram long-poll, Discord Gateway) needs none — CUGA reaches out. An inbound one (Slack) needs the outside world to reach CUGA, hence a public route. On Code Engine the platform route is that URL, so even Slack is tunnel-free.

The shared call (what all four channels send)

Channels no longer POST /invoke. Every adapter calls cuga_door.ask(), which POSTs CUGA's /run — CUGA is the door, and it decides chat-vs-arming. /invoke is now only the fire seam (scheduler, webhooks); see /invoke & Concierge.

POST http://127.0.0.1:7860/run        # CUGA — header: X-Gateway-Token: <GATEWAY_TOKEN>
{
  "query":     "what's the price of bitcoin?",  # user message, mention stripped by the gate
  "thread_id": "gw:slack:C123#1712…",           # memory locus AND delivery address
  "channel": {                              # identity + delivery target ride together
    "name":      "slack",                    # slack | discord | telegram | web
    "native_id": "C123",                     # the DELIVERY address (channel/chat id)
    "user":      "U456",                     # the AUTHOR's native id → per-user identity/scope
    "thread_id": "gw:slack:C123#1712…"
  }
}
// response → { "ok": true, "answer": "Bitcoin is trading at …", "thread_id": "…" }
//   plus "routed_to": "events" when CUGA forwarded it to the concierge instead of answering

The only per-channel differences are channel.name, the thread_id prefix, and what native_id means natively (a Slack channel, a Telegram chat, a Discord channel). Everything downstream is channel-agnostic. The #<locus> suffix keys per-topic memory; channel_native_id strips it so delivery is unaffected by threading.

Telegram direct · long-poll

CUGA runs an outbound getUpdates loop as a boot background task. No webhook, no public URL.

Transport: outbound HTTPS long-poll · Handler: _telegram_answer · Started: app.state.events_background at boot
1
CUGA ──▶ Telegram
GET api.telegram.org/bot<token>/getUpdates?offset=N&timeout=25&allowed_updates=["message"]
The request hangs up to 25 s until a message arrives; offset acks the last update so each is delivered once. (run_poller, telegram_direct.py.)
2
Telegram ──▶ CUGA (response body)
200 { ok, result: [ { update_id, message } ] }
Filtered by should_process (has text + chat.id, sender not a bot) then mention_gate (private chat always passes; a group needs @<bot> under EVENTS_TELEGRAM_CHAT=mention).
3
adapter ──▶ CUGA /run (the door)
cuga_door.ask() → POST 127.0.0.1:7860/run · channel.name="telegram", thread_id="gw:telegram:<chat_id>", user=<sender_id>
CUGA decides: plain chat → the supervisor answers; a slash verb (or an open arming dialogue) → forwarded to the eventing service. Returns {answer}.
4
CUGA ──▶ Telegram
POST api.telegram.org/bot<token>/sendMessage { chat_id, text, reply_to_message_id }
Answer posts back as a threaded reply to the asking message_id. (text capped 4096.)

Raw envelopes

// ② getUpdates response — Telegram → CUGA
{ "ok": true, "result": [ {
    "update_id": 870123456,                // next poll uses offset = this + 1
    "message": {
      "message_id": 42,                    // becomes reply_to_message_id
      "from": { "id": 111222333, "is_bot": false, "username": "anu" },
      "chat": { "id": 111222333, "type": "private" },  // private → mention gate passes
      "text": "what's the price of bitcoin?" } } ] }

// ③ /invoke — CUGA handler → CUGA
{ "text": "what's the price of bitcoin?", "agent": "concierge", "deliver": false,
  "source": { "type": "channel", "name": "telegram",
              "thread_id": "gw:telegram:111222333", "user": "111222333" },
  "event": { "kind": "message", "payload": { "telegram_user": "111222333" } } }

// ④ sendMessage body — CUGA → Telegram
{ "chat_id": 111222333, "text": "Bitcoin is trading at …", "reply_to_message_id": 42 }

Discord direct · Gateway

CUGA holds a persistent WebSocket to Discord's Gateway. Outbound socket → no public URL. Requires Message Content Intent in the Developer Portal (env EVENTS_DISCORD_MEMBERS_INTENT=1 additionally requests the members intent).

Transport: outbound WebSocket · Handler: _discord_answer · Gateway: wss://gateway.discord.gg/?v=10
1
CUGA ──▶ Discord Gateway (connect + identify)
HELLO (op 10) → IDENTIFY (op 2: token, intents) → heartbeat (op 1) · on READY, learn own bot id
The socket stays open; op 7/9 trigger a reconnect + fresh IDENTIFY. (run_gateway, discord_direct.py.)
2
Discord ──▶ CUGA (dispatch)
op 0 t=MESSAGE_CREATE { d: { id, channel_id, guild_id, content, author:{id,bot}, mentions } }
Filtered by should_process (content + channel, author not a bot) and mention_gate (DM = no guild_id passes; else @bot or a reply to the bot).
3
adapter ──▶ CUGA /run (the door)
cuga_door.ask() → POST 127.0.0.1:7860/run · channel.name="discord", thread_id="gw:discord:<channel_id>", user=<author_id>
Shared envelope; event.payload.discord_user.
4
CUGA ──▶ Discord REST
POST discord.com/api/v10/channels/<channel_id>/messages { content, message_reference } · Authorization: Bot <token>
Answer posts as a reply referencing the asking message id. (content capped 2000.)

Raw exchange — the Gateway handshake

// HELLO — Gateway → CUGA (op 10): heartbeat interval (ms)
{ "op": 10, "d": { "heartbeat_interval": 41250 } }

// IDENTIFY — CUGA → Gateway (op 2). intents bitmask requests GUILDS|GUILD_MESSAGES|MESSAGE_CONTENT
{ "op": 2, "d": { "token": "<bot_token>", "intents": <bitmask>,
                "properties": { "os": "linux", "browser": "cuga", "device": "cuga" } } }

// READY — Gateway → CUGA (op 0, t=READY): our own bot id (for the mention gate)
{ "op": 0, "t": "READY", "d": { "user": { "id": "<bot_id>", "bot": true }, "session_id": "…" } }

// ② MESSAGE_CREATE — Gateway → CUGA (op 0)
{ "op": 0, "t": "MESSAGE_CREATE", "d": {
    "id": "1170000000000000000",           // message id — used as reply target
    "channel_id": "1160000000000000000",
    "guild_id": "1150000000000000000",     // absent in a DM → mention gate passes
    "content": "<@bot> what's the price of bitcoin?",
    "author": { "id": "1400000000000000000", "bot": false },
    "mentions": [ { "id": "<bot_id>" } ] } }

// ③ /invoke — CUGA handler → CUGA
{ "text": "what's the price of bitcoin?", "agent": "concierge", "deliver": false,
  "source": { "type": "channel", "name": "discord",
              "thread_id": "gw:discord:1160000000000000000", "user": "1400000000000000000" },
  "event": { "kind": "message", "payload": { "discord_user": "1400000000000000000" } } }

// ④ REST reply body — CUGA → Discord
{ "content": "Bitcoin is trading at …",
  "message_reference": { "message_id": "1170000000000000000", "fail_if_not_exists": false } }

Slack direct · Events API

Slack pushes events to a URL you configure — so this one is inbound and needs a public URL (the CE route, or a dev tunnel). Still no AP.

Transport: inbound webhook · Handler: slack_events → _slack_answer · Needs: EVENTS_PUBLIC_URL
0
one-time setup
Slack app → Event Subscriptions → Request URL = <EVENTS_PUBLIC_URL>/api/events/slack/events · subscribe message.channels
Slack first sends a url_verification challenge; CUGA echoes it back to confirm the endpoint.
1
Slack ──▶ CUGA
POST <public>/api/events/slack/events { type:"event_callback", event:{ type:"message", channel, user, text, ts, thread_ts } }
Headers X-Slack-Signature + X-Slack-Request-Timestamp are HMAC-verified against SLACK_SIGNING_SECRET before anything runs. Dedup on event.ts.
2
CUGA ──▶ Slack (immediate ACK)
200 {ok:true} — returned at once; _slack_answer runs in the background
Slack's ACK deadline is ~3 s, so CUGA acks first and posts the reply out-of-band. Slack never times out and retries.
3
adapter ──▶ CUGA /run (the door)
cuga_door.ask() → POST 127.0.0.1:7860/run · channel.name="slack", thread_id="gw:slack:<channel>#<thread_ts>", user=<U…>
The #<thread_ts> suffix scopes memory per-thread; the bare channel is used for identity/delivery.
4
CUGA ──▶ Slack Web API
POST slack.com/api/chat.postMessage { channel, text, thread_ts } · Authorization: Bearer <bot_token>
The reply posts back into the same thread.

Raw envelopes

// ⓪ url_verification (first time you save the Request URL)
// Slack → CUGA  { "type": "url_verification", "challenge": "3eZbrw1a…" }
// CUGA → Slack  200 { "challenge": "3eZbrw1a…" }

// ① event_callback — Slack → /api/events/slack/events
//    headers: X-Slack-Signature: v0=<hmac>   X-Slack-Request-Timestamp: 1730000000
{ "type": "event_callback", "team_id": "T012AB",
  "event": { "type": "message", "channel": "C0BEYJ9NATB", "user": "U0123ABCD",
              "text": "what's the price of bitcoin?",
              "ts": "1730000000.000100", "thread_ts": "1730000000.000100" } }

// signature check: HMAC-SHA256(signing_secret, "v0:" + ts + ":" + raw_body) == X-Slack-Signature

// ③ /invoke — CUGA handler → CUGA  (thread_ts folded into thread_id)
{ "text": "what's the price of bitcoin?", "agent": "concierge", "deliver": false,
  "source": { "type": "channel", "name": "slack",
              "thread_id": "gw:slack:C0BEYJ9NATB#1730000000.000100", "user": "U0123ABCD" },
  "event": { "kind": "message", "payload": { "slack_user": "U0123ABCD" } } }

// ④ chat.postMessage body — CUGA → Slack  (Authorization: Bearer <bot_token>)
{ "channel": "C0BEYJ9NATB", "text": "Bitcoin is trading at …", "thread_ts": "1730000000.000100" }
Slack also delivers non-message events to the same endpoint (app_mention, reactions, member joins…). Those don't go to chat — they feed the direct watchers (a :bug: reaction → the triage agent). See NL→Flow §direct watchers.

Web chat built-in

Two distinct web surfaces — don't conflate them.
  • The main agent chat (the classic CUGA conversation) uses POST /stream (SSE) — exactly as in cuga-main. If a browser message reads as a plain question it streams the agent directly. A slash or standing-intent utterance is routed to the concierge to arm a flow.
  • The concierge box in the Studio uses POST /api/concierge — a separate, synchronous NL surface ("watch/schedule something", /automate). Additive; it does not reroute the agent chat.
Both call concierge.run(…) in-process — no envelope, no /invoke, no deliver hop. The answer comes back in the same HTTP response.
Transport: HTTP request/response & SSE · APIs: /api/concierge (sync) · /stream (streamed)
1
Browser ──▶ CUGA
POST /api/concierge { text, thread_id } — or POST /stream (X-Thread-ID header)
The browser session authenticates the caller (no X-Gateway-Token — that's only for the channel→/invoke hop). thread_id keys memory like every other channel.
2
CUGA ──▶ Browser (same response)
/api/concierge → 200 { ok, reply, scope, trace_id } · /stream → text/event-stream frames
Synchronous: the answer is the response — one fewer round trip than the network channels.
// /api/concierge — request → response
POST /api/concierge   { "text": "what's the price of bitcoin?", "thread_id": "web:local" }
200 { "ok": true, "reply": "Bitcoin is trading at …", "scope": "default/…", "trace_id": "…" }

The web endpoint returns the text under reply; the internal channel→/invoke hop returns it under answer. Same content, two endpoints.

The filters — should_process & mention_gate

Before any message reaches the seam, two filters run. They protect against loops (a bot answering itself) and control who the bot responds to.

FilterWhat it drops / requiresPer channel
should_processneeds text + channel/chat id; rejects bot-authored messages (no self-reply); Slack also drops subtype/bot_id and dedups on ts telegram_direct · discord_direct · slack_direct
mention_gatecontrolled by EVENTS_<CHANNEL>_CHAT: all (default — every message reaches the concierge) or mention (a private/DM chat always passes; a group/channel needs @bot, a reply-to-bot, or a bot-in-thread) all three; Slack's is async (checks conversations.replies)

A message gated out of chat can still feed the direct watchers (armed "when someone posts in #x…" flows) — the gate is about the conversational reply, not about dropping the event entirely.

Isolation. One CUGA server binds one bot per channel (single *_BOT_TOKEN) — one Telegram poller, one Discord Gateway, one Slack endpoint. Within a bot, many users are isolated by scope (tenant/instance/user, resolved from source.user via the identity map) and by thread (thread_id). Per-user isolation activates once a user links their channel id (/start <token>); unlinked senders share the default scope.
