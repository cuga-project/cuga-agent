Channels & the No-AP Path

How each chat channel reaches CUGA — the APIs, the transports, and the exact data envelopes — and how to run the whole events layer with zero Activepieces.

1 · TL;DR — what needs AP, what doesn't

Every channel converges on one internal seam: POST /invoke. What differs is only how a message gets to CUGA. Three of four channels are AP-free today; the fourth (Telegram) is now AP-free by default too.

ChannelBackendTransport to CUGANeeds AP?Needs public URL?
webbuilt-inHTTP /api/conciergenono
telegramdirect · long-poll new defaultoutbound getUpdatesnono
discorddirect · Gatewayoutbound WebSocketnono
slackdirect · Events APIinbound webhooknoyes — Slack POSTs to you
telegramAP · webhook legacyTelegram → AP → CUGAyesyes (AP tunnel)

The distinction that matters: an outbound transport (Telegram long-poll, Discord Gateway) needs no public URL because CUGA reaches out; an inbound one (Slack) needs the outside world to reach CUGA, hence a tunnel.

2 · Capability tiers (with / without AP)

The server prints this as a capability report at boot (also at GET /api/events/status). Nothing fails without AP — the unavailable tiers degrade cleanly.

TierWhat you getAP?
Tier 0web · Telegram-direct · Discord-direct · webhooks · NOW/chat trigger · direct channel-message watchersnone

The "now" trigger works with zero AP. A user DMs the Telegram bot, @mentions the Discord bot, or opens the web chat → the concierge answers → the reply goes back. No Activepieces, no tunnel (except Slack). This is Tier 0.

4 · The one seam — the /invoke envelope

Every channel's inbound handler normalizes its native message into the same envelope and POSTs it to CUGA's internal /invoke. This is why adding/decoupling a channel never touches the agent, delivery, or the Studio — they all sit behind this contract.

POST http://127.0.0.1:7860/invoke        # header: X-Gateway-Token: <GATEWAY_TOKEN>
{
  "text":   "what's the price of bitcoin?",   # the user's message (mention stripped)
  "agent":  "concierge",
  "deliver": false,                          # channel sends the reply itself (round-trip)
  "source": {
    "type": "channel",
    "name": "telegram",                     # telegram | discord | slack
    "thread_id": "gw:telegram:<chat_id>",   # keys per-conversation memory
    "user": "<sender_id>"                    # per-user identity (creds/perms once linked)
  },
  "event": { "kind": "message", "payload": { "telegram_user": "<sender_id>" } }
}
// response → { "answer": "Bitcoin is trading at …" }

thread_id uses the gw:<channel>:<native_id> shape (Slack adds #<thread_ts> for per-thread memory). deliver:false means the channel handler owns the round-trip — it takes the answer and posts it back itself.

Inside the door — what /invoke and the concierge actually do

The envelope arrives; here's the path from there to a real agent answer. Every channel shares it.

Step A — /invoke guards, scopes, then routes

The handler authenticates, validates the envelope, resolves the tenant/user scope (isolation — the channel author's native id → a user via the identity map), handles bounded-run expiry and the /start <token> account-link, then forks on agent:

# app.py — POST /invoke, after auth + envelope + scope resolution
if agent == "concierge":                                  # channels arm agent="concierge" → the router
    answer = await concierge.run(env.thread_id, env.text, principal)
else:                                                    # a concrete agent id runs directly
    answer = await runtime.run(agent, env.thread_id, env.worker_input(), scope=agent_scope)
# then: append a metadata footer (who answered + tools used), and deliver if deliver=True

Channel messages carry agent:"concierge", so a chat from Telegram/Slack/Discord goes into concierge.run — the runtime router.

Step B — the concierge decides: chat, or arm a flow?

This is the whole point of the concierge. It is not an LLM wrapper around every message — a plain question skips the LLM entirely and goes straight to the agent. The decision, in order:

# concierge.py — run(): the routing rule, every surface
parsed = _slash_parse(text)                    # 1. /watch /schedule /cron /poll /push → deterministic arm
if parsed is not None:
    return await self._arm_slash(thread_id, p, parsed)

pre = await self._pre_route(thread_id, p, text)  # 2. high-confidence "watch X" → arm it (or ask 1 Q)
if pre is not None:
    return pre

if classify.classify(text) == "NOW":            # 3. a regular question → STRAIGHT to the agent,
    return await self._runtime.run(              #    NO concierge-LLM hop (the NOW fast-path)
        THE_AGENT, p.thread(f"{thread_id}:cuga"), text, scope=p.agent_scope)

# 4. else — standing intent (cron/poll/push phrasing): the LLM react-agent decides, using its
#    tools answer_now(agent='cuga', task) and find_or_create_flow(kind, source, event, …)

So a chat (“what's IBM's stock price?”) is classified NOW and runs the agent directly. Only standing phrasing (“every weekday…”, “when a PR opens…”) engages the concierge's own LLM, whose answer_now tool also calls runtime.run('cuga', …) — same agent, either way.

Step C — running the REAL CUGA agent (the same path /stream uses)

runtime.run builds/reuses the agent's DynamicAgentGraph and drives it with CUGA's AgentLoop — identical to what the browser's /stream endpoint does. It's a streaming graph; we consume the stream to the final answer:

# _cuga_bridge.py — run_graph(): "Run a DynamicAgentGraph to a final answer — the SAME path /stream uses"
from cuga.backend.cuga_graph.state.agent_state import default_state
from cuga.backend.cuga_graph.utils.agent_loop import AgentLoop, AgentLoopAnswer

state = default_state(page=None, observation=None, goal="")
state.input = text                               # the user's message IS the agent's query

loop = AgentLoop(thread_id=tid, graph=graph.graph,   # the compiled StateGraph (real CUGA)
                 policy_system=graph.policy_system, tracker=tracker, ...)

answer = ""
async for event in loop.run_stream(state=state):     # drive the graph; collect the final answer
    if isinstance(event, AgentLoopAnswer):
        if event.tools:  runmeta.add(tools=[t.name for t in event.tools])  # for the footer
        if event.answer is not None:  answer = event.answer
        if event.end:  break
return answer

This is why the earlier claim holds literally: web chat (/stream), channels (/invoke → concierge → answer_now), and the automate box (/api/concierge) all converge on the same DynamicAgentGraph. One brain, three doors — the agent itself is never forked.

The whole path, one line: envelope → /invoke (auth · scope · expiry · link) → route on agent → concierge.run → { slash-arm · pre-route-arm · NOW → agent · LLM-router } → runtime.run('cuga') → DynamicAgentGraph via AgentLoop → answer → metadata footer → deliver.

5 · Telegram direct · long-poll

CUGA runs an outbound getUpdates loop. No webhook, no public URL, no AP.

Transport: outbound HTTPS long-poll · APIs: Telegram Bot API + /invoke · Started: boot background task
1
CUGA ──▶ Telegram
GET api.telegram.org/bot<token>/getUpdates?offset=N&timeout=25&allowed_updates=["message"]
Long-poll: the request hangs up to 25s until a message arrives. offset acks the last update so each is delivered once.
2
Telegram ──▶ CUGA (response body)
200 { ok, result: [ { update_id, message } ] }
Each message = { message_id, from:{id,is_bot,username}, chat:{id,type}, text }. Filtered by should_process (has text + chat id, sender not a bot) and the mention_gate.
3
CUGA handler ──▶ CUGA /invoke
POST 127.0.0.1:7860/invoke · source.name="telegram", thread_id="gw:telegram:<chat_id>"
The normalized envelope (§4). Concierge runs, returns {answer}.
4
CUGA ──▶ Telegram
POST api.telegram.org/bot<token>/sendMessage { chat_id, text, reply_to_message_id }
The answer is posted back as a threaded reply to the asking message.

Raw envelopes

// ② getUpdates response — Telegram → CUGA
{
  "ok": true,
  "result": [ {
    "update_id": 870123456,          // next poll uses offset = this + 1
    "message": {
      "message_id": 42,
      "from": { "id": 111222333, "is_bot": false, "username": "anu" },
      "chat": { "id": 111222333, "type": "private" },   // type: private|group|supergroup
      "date": 1730000000,
      "text": "what's the price of bitcoin?"
    }
  } ]
}

// ③ /invoke — CUGA handler → CUGA  (the normalized envelope, §4)
{ "text": "what's the price of bitcoin?", "agent": "concierge", "deliver": false,
  "source": { "type": "channel", "name": "telegram",
              "thread_id": "gw:telegram:111222333", "user": "111222333" },
  "event": { "kind": "message", "payload": { "telegram_user": "111222333" } } }

// ④ sendMessage body — CUGA → Telegram
{ "chat_id": 111222333, "text": "Bitcoin is trading at …", "reply_to_message_id": 42 }

6 · Discord direct · Gateway

CUGA holds a persistent WebSocket to Discord's Gateway. Outbound socket → no public URL, no AP. ⚠ Requires Message Content Intent in the Developer Portal.

Transport: outbound WebSocket (wss) · APIs: Discord Gateway v10 + REST + /invoke
1
CUGA ──▶ Discord Gateway (connect + identify)
wss://gateway.discord.gg/?v=10 → HELLO → IDENTIFY (op 2: token, intents) → heartbeat (op 1)
On READY, CUGA learns its own bot id (for the mention gate). The socket stays open; reconnects on drop.
2
Discord ──▶ CUGA (dispatch)
MESSAGE_CREATE { d: { id, channel_id, guild_id, content, author:{id,bot}, mentions } }
Filtered by should_process (text + channel, author not a bot) and the mention_gate (in mention mode, DMs/replies/@bot pass).
3
CUGA handler ──▶ CUGA /invoke
POST 127.0.0.1:7860/invoke · source.name="discord", thread_id="gw:discord:<channel_id>"
Same envelope shape as §4 (event.payload.discord_user).
4
CUGA ──▶ Discord REST
POST discord.com/api/v10/channels/<channel_id>/messages { content, message_reference } · Authorization: Bot <token>
The answer is posted as a reply referencing the asking message.

Raw exchange — the full Gateway handshake

Discord's Gateway is a stateful op-code protocol over one WebSocket. The opening handshake (HELLO → IDENTIFY → READY) runs once per connection; heartbeats run forever; op 7/9 trigger a reconnect. This is what run_gateway speaks.

// on connect — Gateway → CUGA (op 10 HELLO): tells us the heartbeat interval
{ "op": 10, "d": { "heartbeat_interval": 41250 } }        // ms

// ① IDENTIFY — CUGA → Gateway (op 2). intents 33283 = GUILDS | GUILD_MESSAGES |
//    GUILD_MESSAGE_REACTIONS | MESSAGE_CONTENT (the privileged one)
{ "op": 2, "d": { "token": "<bot_token>", "intents": 33283,
                "properties": { "os": "linux", "browser": "cuga", "device": "cuga" } } }

// heartbeat loop — CUGA → Gateway (op 1) every heartbeat_interval; d = last seq seen (or null)
{ "op": 1, "d": null }
// Gateway → CUGA (op 11) ACK. (Gateway may also send op 1 to demand an immediate heartbeat.)
{ "op": 11 }

// READY dispatch — Gateway → CUGA (op 0, t=READY): we learn our own bot id (for the mention gate)
{ "op": 0, "t": "READY", "s": 1,
  "d": { "user": { "id": "<bot_id>", "username": "cuga", "bot": true },
        "session_id": "a1b2c3…" } }

// reconnect signals — Gateway → CUGA: op 7 (please reconnect) / op 9 (invalid session).
// run_gateway breaks the inner loop and re-IDENTIFYs (fresh session; no resume).
{ "op": 7 }        // or { "op": 9, "d": false }

// ② MESSAGE_CREATE dispatch — Gateway → CUGA (op 0)
{ "op": 0, "t": "MESSAGE_CREATE", "s": 5,
  "d": {
    "id": "1170000000000000000",          // message id — used as reply_to
    "channel_id": "1160000000000000000",
    "guild_id": "1150000000000000000",    // absent in a DM → mention gate passes
    "content": "<@bot> what's the price of bitcoin?",
    "author": { "id": "1400000000000000000", "username": "anu", "bot": false },
    "mentions": [ { "id": "<bot_id>" } ],
    "referenced_message": null
  } }

// ③ /invoke — CUGA handler → CUGA
{ "text": "what's the price of bitcoin?", "agent": "concierge", "deliver": false,
  "source": { "type": "channel", "name": "discord",
              "thread_id": "gw:discord:1160000000000000000", "user": "1400000000000000000" },
  "event": { "kind": "message", "payload": { "discord_user": "1400000000000000000" } } }

// ④ REST reply body — CUGA → Discord
{ "content": "Bitcoin is trading at …",
  "message_reference": { "message_id": "1170000000000000000", "fail_if_not_exists": false } }

7 · Slack direct · Events API

Slack pushes events to a URL you configure — so this one is inbound and needs a public URL (CUGA's own tunnel, not AP's). Still no AP.

Transport: inbound webhook (Slack → you) · APIs: Slack Events API + Web API + /invoke · Needs: EVENTS_PUBLIC_URL
0
one-time setup
Slack app → Event Subscriptions → Request URL = <EVENTS_PUBLIC_URL>/api/events/slack/events · subscribe message.channels
Slack first sends a url_verification challenge; CUGA echoes it back to confirm the endpoint.
1
Slack ──▶ CUGA
POST <public>/api/events/slack/events { type:"event_callback", event:{ type:"message", channel, user, text, ts, thread_ts } }
Headers X-Slack-Signature + X-Slack-Request-Timestamp are verified against SLACK_SIGNING_SECRET (HMAC over v0:ts:body) before anything runs.
2
CUGA handler ──▶ CUGA /invoke
POST 127.0.0.1:7860/invoke · source.name="slack", thread_id="gw:slack:<channel>#<thread_ts>"
The #<thread_ts> suffix scopes memory per-thread; the native id (for identity/delivery) is the bare channel.
3
CUGA ──▶ Slack Web API
POST slack.com/api/chat.postMessage { channel, text, thread_ts } · Authorization: Bearer <bot_token>
The reply posts back into the same thread.
Slack ACKs must be fast: CUGA returns 200 immediately and runs the concierge in the background (the reply arrives via chat.postMessage), so Slack never times out and retries.

  "type": "event_callback",
  "event": {

8 · Web chat built-in

Two distinct web surfaces — don't conflate them.
  • The main agent chat (the "good old" CUGA conversation, ChatLanding) uses POST /stream + /api/conversation-* — exactly as in cuga-main, untouched by the events layer. If you just want to talk to the agent in the browser, that's the endpoint, and it hasn't changed.
  • The concierge chat (this section) is a separate events-only box in the Studio — "ask me to watch / schedule something / /automate". It uses POST /api/concierge. It's additive; it does not replace or reroute the agent chat.
Both ultimately run the same agent (/invoke and /stream share the same DynamicAgentGraph path). Different doors, one brain.

The rest of this section describes the concierge surface (/api/concierge) — the events "web channel". Like the main chat it's synchronous: the answer comes back in the HTTP response, no callback, no "deliver" hop. No channel transport, no AP, no tunnel — ever.

Transport: HTTP request/response (synchronous) · API: /api/concierge
1
Browser ──▶ CUGA
POST /api/concierge { text, thread_id }
The browser session authenticates the caller (no X-Gateway-Token needed — that's for the channel→/invoke hop). thread_id keys per-conversation memory just like the other channels.
2
CUGA ──▶ Browser (same response)
200 { answer, thread_id, ... }
Rendered directly in the chat UI. Because it's synchronous, deliver is implicit — the answer is the response.

Raw envelopes

// ① request — Browser → CUGA
POST /api/concierge
{ "text": "what's the price of bitcoin?", "thread_id": "web:local" }

// ② response — CUGA → Browser  (answer inline under "reply"; no callback, no deliver hop)
200 { "ok": true, "reply": "Bitcoin is trading at …", "trace_id": "…" }

The web endpoint returns the text under reply; the internal channel→/invoke hop (§4) returns it under answer. Same content, two endpoints.

Contrast with the channels: they post an internal envelope to /invoke with deliver:false and then send the reply back over their own transport. Web skips both hops — /api/concierge runs the same concierge and hands the answer straight back. Same agent, same memory model, one fewer round trip.

11 · Isolation & multi-bot — one app per channel, per server

Short version: one CUGA server is bound to one bot/app per channel. One Telegram bot, one Slack app, one Discord bot. You cannot run multiple bots of the same channel on a single server today.

The channel tokens are single values the server reads once — TELEGRAM_BOT_TOKEN, SLACK_BOT_TOKEN (+ SLACK_SIGNING_SECRET), DISCORD_BOT_TOKEN — so there's exactly one Telegram poller, one Discord Gateway, and one Slack endpoint per process. There is no bot registry to multiplex more than one.

Three isolation axes — the bot is NOT the finest grain

"One bot per server" does not mean "one user per server". Isolation happens at three levels; the bot is only the outermost.

AxisGranularityMechanismMultiple per server?
App / botone bot per channelsingle token env var (*_BOT_TOKEN)no — one only
Tenant / usermany users within one botscope = tenant/instance/user, via the identity mapyes
Threadper conversationthread_id = gw:<channel>:<native>yes

When a message arrives, /invoke resolves the sender's native id → a user → a scope, and everything keys off scope: conversation memory, agent lookup, subscriptions, and AP credentials/connections. So a single bot safely serves many end-users — User A and User B on the same bot get separate memory and their own connected integrations.

⚠ The per-user isolation needs linking. An end-user is only isolated once they've linked their channel identity (the /start <token> account-link flow). An unlinked sender falls back to the default/operator scope — so without linking, one bot behaves as one identity (shared memory + credentials). Link users before treating a shared bot as multi-tenant.

So how do you run multiple bots?

ScenarioApproach
A few distinct apps / brands One CUGA server per app (today's model). Each deployment = its own token set, port, and (for Slack) its own public URL. Process-level isolation, and it maps cleanly to one Code Engine app each. supported now
Many tenants on one server (SaaS) Needs a bot registry — (channel, bot_id) → {token, tenant_scope, agent_roster} — plus one transport per bot and inbound routing "which bot got this → which tenant". not built yet
Slack is the exception worth knowing. Slack's native model is one app, many workspaces via OAuth — every event carries a team_id. So of the three, Slack is the one built for one-app-many-tenants (add an install store + route by team_id). Telegram/Discord would instead need N distinct bot tokens. Today CUGA's Slack uses a single workspace token, so it's one-app like the rest — but it's the natural first candidate for multi-tenant.

12 · Cloud deploy (Code Engine) — tunnel-free

The tunnel (ngrok / cloudflared) exists for one reason: to give a laptop a public HTTPS URL. Deploy CUGA to Code Engine (or any PaaS with ingress) and that reason disappears — the platform route is your public URL. So every channel works without a tunnel.

ChannelWhy it works on CE with no tunnel
webserved by the app itself — it's just the CE route.
telegram discordoutbound (long-poll / Gateway) — CUGA reaches out; never needed inbound reachability.
slack · OAuth · AP webhooksinbound — set the Request URL / redirect URI to the CE route; it replaces the tunnel 1:1.

Set EVENTS_PUBLIC_URL to the CE route (https://<app>.<region>.codeengine.appdomain.cloud) so Slack's events_url and OAuth callbacks resolve. That's the whole tunnel replacement.

⚠ Two CE-specific caveats — they're about the OUTBOUND channels, and they're real:
  • Don't scale to zero. Telegram long-poll and the Discord Gateway are persistent loops — a scaled-to-zero instance runs no loop and misses messages. Set min-scale = 1 for the events workload. (Bonus: it also avoids cold-starts blowing Slack's ~3s ACK deadline.)
  • Single instance for the pollers. N replicas each open their own long-poll / Gateway → duplicate message processing. Pin the poller/Gateway component to min = max = 1 (a singleton). Stateless inbound (Slack / web / webhook) can scale horizontally behind the same route.
The clean topology: one always-on singleton for the outbound channels + a horizontally scalable pool for inbound. If you deploy AP too, give it its own CE app + route (no tunnel there either) and point CUGA at it over the private network.

Answer to "can we use these channels without a tunnel on CE?" — yes. Web + Telegram + Discord need no inbound reachability at all; Slack/OAuth use the CE route in place of the tunnel. The only new work is pinning the outbound-channel component to a single always-on instance.
