Native Events — what shipped, what's next

A ~12–14h push that made CUGA event-driven without Activepieces — plus the plan, the pitch, and the honest list of what's still pending.

1 · TL;DR

CUGA can now watch, schedule, and act on its own — with zero Activepieces. A native in-process scheduler runs cron/poll; the concierge decides native-vs-AP per utterance; Telegram/Discord/web run AP-free; and a set of rich, filterable APIs expose every watcher and run. AP stays — but only where it earns it (the 754 managed integration triggers).

The one-line shift: Activepieces went from the spine to one backend. The concierge routes a timer or a tool-watch to our scheduler (no AP), and an integration event (gmail/github/box) to AP. One seam — /invoke — underneath both.

3 · The architecture now

Three ways the world reaches CUGA, all landing at one seam — /invoke:

TriggerOwnerNeeds AP?Example
cron / schedulenative❌"every weekday at 9am, brief me"
poll / watch-a-toolnative❌"watch bitcoin every 2 min", "watch my error logs"
webhook (inbound)native❌"POST to /api/events/hook/<name>"
integration eventAP✅"when a new PR opens on my repo" (github piece)
channels (converse)web·Telegram·Discord = direct · Slack = direct+URL · Telegram-AP = opt-inmostly ❌chat from any surface
Why keep AP at all? It owns the one genuinely hard thing: 754 maintained OAuth connectors + token lifecycle, where the agent never sees a credential. We don't reinvent that. Native owns timers, tool-watches, and webhooks — everything AP structurally can't reach (your own tools) or shouldn't tax you a container for (a cron).

4 · Credentials — who holds what (confirmed)

Integrations — AP holds them

github / gmail / box / calendar / pinterest are per-user (ownership: per-user, ADR 0003): each chatting user authorizes their own OAuth/token, and Activepieces stores it encrypted. The agent never sees the credential — it gets event content, AP does the authenticated call. Connections are keyed per principal (isolation).

Tools — CUGA manages them

If a tool (an MCP tool the agent calls) needs a credential, that's CUGA's to manage — AP has no piece for it. This is the deliberate trade of moving tool-watching/actions to CUGA: the tool (or CUGA) owns the token. Same isolation model (per-user scope), different vault.

So your instinct is right: integration creds live in AP (per-user, safe); tool creds are CUGA's job. The line is exactly "is there an AP piece for it?"

7 · The pitch & stopping point

CUGA becomes a platform, not an integration list: it watches anything (a tool, a clock, a webhook, or a SaaS event), reasons with the right sub-agent, and delivers to any channel — running with or without Activepieces, on a laptop or in the cloud.

A good stopping point — three PRs

PRContents
① Native-events (no-AP route)The native scheduler + routing + Telegram-direct + the run/watcher/dry-run APIs + no-AP make targets + docs. AP behind a feature flag. This is the bulk of what shipped.
② ChannelsTelegram/Discord/Slack/web AP-free channels + delivery + the capability report. (Can fold into ①, or stand alone for review.)
③ AP route + integrationsKeeps the AP path green (integration push), and we keep adding integrations here over time — AP is the extensible connector shelf. Pair with a cuga-apps demo.
On "the AP thingie — we keep adding more, right?" Yes. AP is the connector shelf: each new SaaS trigger is a data row (registry), not engine code. Native handles timers/tools/webhooks; AP grows sideways with more integrations. The two never collide — one owner per subscription, decided at arm time.

Recommended finish line for this chapter: land ① (+② folded in), keep ③ green with a regression pass, ship the mock dashboard as the UX north-star, and open the SDK-events + Phase-3-poll as the next chapter.
