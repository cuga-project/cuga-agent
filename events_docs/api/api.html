CUGA Event-Driven Agents — API Reference

Every HTTP endpoint the eventing service (cuga-events-svc, :8100) exposes: the /invoke fire seam, the concierge, the Studio read endpoints, connect/credential flows, the direct Slack webhook, and admin.
These are NOT on CUGA. CUGA (:7860) exposes the door (POST /run), /stream and GET /run/agents; channel messages go there and CUGA forwards to /api/concierge only for arming.
The action half (trigger ▸ agent ▸ ACTION) added no new endpoints — it rides POST /api/concierge at arm time; direct-trigger actions fire a reusable executor flow internally. So this reference stays complete.

0 Conventions

Auth & identity

  • /invoke is gateway-only: requires header X-Gateway-Token: <GATEWAY_TOKEN> (401 otherwise). It's the callback seam every AP flow / trigger uses.
  • All other endpoints resolve a Principal from headers (or a scope/?scope= override): tenant/instance/user. Isolation is by scope — you only see your own subscriptions/connections.
  • Admin endpoints (/admin/*) require an admin role in the user store → 403 otherwise.

Shapes

  • Requests & responses are JSON. Errors are {"ok":false,"error":"…"} with a matching status.
  • Most write endpoints echo {"ok":true, …}; reads return the resource directly.
  • A trace_id rides on /invoke and /api/concierge for correlation.

1 Core — the reasoning seam

POST/invoke the callback seam · gateway-token only

Every trigger (AP flow, schedule, channel webhook) calls back here. agent:"cuga" runs the one agent directly on the worker runtime — its supervisor picks the specialist internally per wake-up; agent:"concierge" routes to the NL→flow router instead. (cuga is the only addressable worker; a sub-agent name is not — it 404s as "unknown agent".) The reply carries a metadata footer and structured meta (who answered + tools). This is also where direct-channel delivery happens (see the callout below).

Request body
{
  "agent": "cuga",               // the one agent · or "concierge" for the NL→flow router
  "text":  "what moved in crypto today?",
  "thread_id": "gw:slack:C123",   // conversation key; gw:<channel>:<native> for channels
  "deliver": false,             // true → CUGA owns delivery (direct channel or EA_CAPTURE_URL)
  "scope": "acme/inst/alice",      // optional tenant scope (set by AP when the flow was armed)
  "source": { "type": "channel", "name": "slack", "thread_id": "gw:slack:C123#169.9", "user": "U_ALICE" }, // user = the AUTHOR → per-user identity; #<ts> = per-thread memory
  "event":  { "kind": "message", "payload": {} }
}
Response
{
  "ok": true,
  "agent": "cuga",
  "answer": "Bitcoin +3.1% …\n\n— cuga · via cuga-finance · 4.2s",
  "trace_id": "tr_…",
  "meta": { "agent": "cuga", "backend": "cuga", "hint": "pricebot", // supervisor's internal pick
            "mcp": ["cuga-finance"], "tools": ["…"], "ms": 4200 }
}

Also handles: account-linking (/start <token> / /link <token> from a channel binds the sender's native id → profile), and EVENTS_REPLY_METADATA=0 to suppress the footer.

Direct-channel delivery (deliver=true)

When deliver:true and source.type=="channel" and the channel's backend is direct (delivery.is_direct, e.g. Slack), CUGA sends the answer itself via delivery.send_direct → slack_direct.chat.postMessage — no AP send-step. Otherwise, if EA_CAPTURE_URL is set, the answer is POSTed there (assertable e2e/web sink).

POST/api/concierge NL → flow (LLM router) · ?dry_run=1 for the deterministic plan

The human-facing concierge entry. ?dry_run=1 returns the deterministic planner's decision with no side effects (great for tests/UI preview). Live path runs the LLM concierge (reuse/create + run/arm a flow).

Slash commands are handled here too (concierge.run, same handler from any surface — web chat or channels): /automate <what> is the router-driven one — its heuristic classifier picks the trigger mode (push / cron / poll) from the phrasing, e.g. /automate summarize new emails and message me → PUSH, /automate the market brief every weekday at 8am → CRON, /automate check bitcoin every 5 min on a move → POLL. Five hidden overrides force a mode (/watch = /automate, /push, /schedule, /cron, /poll). Manage the armed flows via the lifecycle endpoints below (subscriptions/<id>/pause · /resume, DELETE subscriptions/<id>, dashboard).

Request
{ "text": "every weekday 8am post a market brief to slack",
  "agent": "cuga", "thread_id": "web:local" }
Response (live)
{ "ok": true, "reply": "ARMED cron for market_briefer → slack (AP flow …)",
  "scope": "acme/inst/alice", "trace_id": "tr_…" }
Response (?dry_run=1)
{ "ok": true, "dry_run": true, "decision": { "mode": "CRON", … }, "flow": {…} }

3 Direct (AP-free) surfaces — Slack · Discord · (Box opt-in)

Discord runs a Gateway WebSocket bot (not an HTTP endpoint): a background task launched from the server lifespan that holds a connection to Discord and, on each message, calls /invoke then replies via the REST API. Default backend (AP polling behind EVENTS_DISCORD_BACKEND=ap); it needs no public URL. Arm returns {backend:"direct"} — nothing to configure.

POST/api/events/slack/events Slack Events API target (this is CUGA, not AP)

Point your Slack app's Event Subscriptions → Request URL here (subscribe bot event message.channels). Handles the one-time url_verification challenge, verifies the Slack signature (SLACK_SIGNING_SECRET), filters bot/edit messages, and for a real human message calls /invoke(concierge) then posts the reply via chat.postMessage.

url_verification handshake
// Slack sends:
{ "type": "url_verification", "challenge": "abc123" }
// CUGA echoes the challenge back as text/plain → 200
event_callback
{ "type": "event_callback",
  "event": { "type": "message", "text": "hi", "channel": "C123", "user": "U1" } }
// → {"ok":true} immediately; the answer is posted back asynchronously.

Env: SLACK_BOT_TOKEN (required) · SLACK_SIGNING_SECRET (recommended). Set EVENTS_SLACK_BACKEND=ap to use the parked AP path instead. See ADR-0008 for the two-backend story.

POST/api/events/box/poll Box direct poll — opt-in (EVENTS_BOX_BACKEND=direct) · gateway-token only

Poll a Box folder for new files and fire the watcher agent on each — the direct Box path that sidesteps AP's OAuth wall and the paid-app webhook. Box's REST API takes a bearer token directly (BOX_DEV_TOKEN, a ~60-min dev token — no OAuth app, no redirect URI, no Gmail). A schedule/cron can drive this endpoint. New files are dispatched through /invoke; deliver_to a direct channel (Slack) uses direct-channel delivery — so the whole chain is AP-free.

Request body
{ "folder_id": "0",           // Box folder to watch (0 = All Files root)
  "since": "2026-07-06T00:00:00-07:00", // created_at baseline (null → all files)
  "agent": "resume_judge",
  "deliver_to": "slack"          // optional: a DIRECT channel sink (CUGA sends)
}
Response
{ "ok": true, "folder": "0",
  "processed": [ { "id": "9", "name": "resume.pdf" } ],
  "newest": "2026-07-06T11:00:00-07:00"  // store as the next `since` }

Env: BOX_DEV_TOKEN or EVENTS_BOX_TOKEN. Verify with tests/events/live_box_direct_check.py. Returns 502 if the token is expired/invalid (Box list fails) so a stale token is loud, not silent.

POST/api/events/hook/<name> generic inbound webhook — no AP, no piece, no connection

Any external system (monitoring, CI, a form, a payment provider) POSTs JSON to <EVENTS_PUBLIC_URL>/api/events/hook/<name>. CUGA serialises the payload into a prompt, runs an agent on it, and optionally delivers the result to a channel. It is a thin wrapper over the same /invoke seam every AP flow uses.

Choosing the agent — two ways:

  • PINNED — ?agent=<agent> (default incident_triage). This exact agent handles every event. Deterministic; best for a high-volume, known source.
  • ROUTED — ?route=1 (aliases true/llm). CUGA picks the best-fit agent the same way the chat concierge does — the caller need not know the agent catalog. It can't ask a clarifying question, so it falls back to a generic triage if nothing fits. The chosen agent is echoed back as agent. Costs one router pass.

Other query: ?deliver_to=<channel> + ?target=<native id> to post the result into e.g. a Slack channel · ?key= — required iff EVENTS_WEBHOOK_KEY is set, compared with hmac.compare_digest. Unset key ⇒ the endpoint is open to anyone who finds the public URL.

# PINNED — you name the agent
curl -X POST "$PUBLIC/api/events/hook/monitoring?agent=incident_triage&deliver_to=slack&target=C0BEYJ9NATB&key=$K" \
  -H 'content-type: application/json' \
  -d '{"alert":"HighCPU","service":"checkout-api","value":97,"threshold":85}'

# ROUTED — lands on the ONE agent (cuga); its supervisor picks the specialist
curl -X POST "$PUBLIC/api/events/hook/stripe?route=1&deliver_to=slack&target=C0BEYJ9NATB&key=$K" \
  -H 'content-type: application/json' \
  -d '{"type":"charge.dispute.created","amount":48000,"reason":"fraudulent"}'
{ "ok": true, "webhook": "stripe", "routed": true,
  "agent": "incident_triage", // ← the concierge's pick "answer": "P1 — payment dispute…" }

401 bad/missing ?key · 502 the internal /invoke call failed. An empty body is accepted — the agent is told (empty body) rather than the request being rejected.

4 Connect & credentials

EndpointWhat it does
GET /api/events/connect/{app}Begin connecting the caller's own account. OAuth app → 302 redirect to consent; token app → tells the UI to POST a token. ?ownership=tenant|per-user, ?agent=, ?return=.
GET /api/events/connect/{app}/callbackOAuth redirect target — passes the code to AP (ensure_oauth_connection; AP does the exchange) and creates the connection. Honors ownership from state.
POST /api/events/connect/{app}/tokenPaste a raw token → a SECRET_TEXT AP connection. Token pieces only (Telegram / Discord bot tokens). OAuth pieces (gmail · box · github · slack) get a clear 400 pointing to the OAuth login. Body {token, ownership?}.
GET /api/events/connectionsThe caller's own AP connections (which integrations they've logged into).

The AP OAuth wall (why token-paste fails for Box/Gmail/Slack-ap)

AP 0.82's UpsertOAuth2Request schema requires the authorization code and does the token exchange itself — it refuses a pre-obtained access/dev/bot token. So OAuth pieces must go through the consent flow (connect/{app} → callback). This is exactly why Slack ships a direct backend that takes the bot token without AP.
