Why the telegram column shows !

Conversation memory is keyed by thread_id. Slack and Discord threads get a #<run> suffix for fresh memory — safe because principal.channel_origin strips # at fire time. Telegram cannot: concierge.find_or_create_flow does its own parse without stripping (concierge.py:262-263), so a suffix would bake chat_id#locus into the AP send step. On a second run the model therefore answers "that's already set up" from memory without calling the arm tool — even though the flow was deleted. That is a real product behaviour, not a harness artefact: delete a flow, ask again, and the concierge tells you it still exists.

What is broken — findings ranked by severity

1. Rotating a token does nothing. bug
ap_engine.ensure_secret_connection (ap_engine.py:465) returns early when the externalId already exists — it never updates the secret. So changing GITHUB_TOKEN in .env, and pasting a fresh PAT into the Studio's Connect button (same function), both silently no-op. AP keeps the old token, GitHub answers 401 Bad credentials when the piece creates the repo webhook, and the concierge relays "reconnect with a token that can manage webhooks", which the model paraphrases as CONNECT NEEDED.
The connect gate is innocent — instrumented, it logs exists=True. The .env PAT is fine: it creates a webhook with HTTP 201. This is the original "I already connected my credentials" mystery.
Fix: update the connection value on mismatch. Workaround: delete the AP connection, then reconnect.

2. support_digest fabricates. bug
It has cuga-web but no source of support tickets, so it Tavily-searches the phrase and dresses up whatever it finds. Observed returning a marketing blog template ("Daily support inbox digest · Clourou") with a source URL, as if those were your overnight tickets. Non-deterministic: ~5 of 7 runs fabricate, ~2 ask for detail.
An agent with a search tool and no data source will always invent an answer. This is the dangerous failure mode — mailbot's and resume_judge's are graceful by comparison, because they ask for the content.
Fix: give it a real ticket source, or make it decline when it has no data.

3. "every 15 minutes … only new items" arms a CRON, not a POLL. bug
Deterministic on both paths — the offline classifier returns {'mode': 'CRON'}, and the LLM concierge agrees. This is the NL→intent seam. It is the single FAIL in the suite.

4. The concierge trusts its memory over the store. gap
After a subscription is deleted, the model still answers "that's already set up" on the same thread — without calling the arm tool, so nothing is created. A sharper variant was observed saying "Cron flow set" having created nothing at all.

5. Slack's endpoint accepts unsigned requests. security
SLACK_SIGNING_SECRET is unset, and slack_direct.verify_signature() returns True for every caller when it is missing. So /api/events/slack/events currently accepts unsigned requests from anyone who finds your public ngrok URL, and can make your agents run. Given Activepieces is already exposed through a cloudflared tunnel, this is worth closing.

6. Integration-backed agents get no tools for their integration. by design
Activepieces owns the credential, so mailbot cannot read Gmail, and resume_judge cannot read Box — they can only process a payload a flow hands them. Same root cause as the Box watcher passing a file's name rather than its content.

7. Pre-existing: one offline test is not isolated. flaky
test_box_poll_endpoint_dispatches_new_files reads the real .box_since.json watermark instead of a temp file and asserts a hard-coded timestamp, so it broke permanently the first time a real Box poll ran. Fails on a pristine checkout; unrelated to this work.

Coverage gaps — what these tests do not prove

Every PUSH case was armed, never fired. No resume was uploaded to Box, no PR was opened, no email was sent to the watched inbox. The suite proves the concierge routes the sentence to the right agent and creates the right Activepieces flow. It says nothing about whether that flow does the right thing when a real event lands. The harnesses that push real data through are live_gmail_e2e.py, live_box_e2e.py and live_github_e2e.py, and they were not run here.

Also unreached by any seeded agent: cuga-web.fetch_webpage_links, cuga-web.search_feeds, cuga-web.get_youtube_video_info, cuga-knowledge.search_semantic_scholar. Four of cuga-web's seven tools now have an agent (webpage_summarizer, video_qa, feed_watcher); before this run the whole fleet reached only web_search.
