1 Architecture

One idea: CUGA is the brain, Activepieces is the nervous system. CUGA reasons and answers; AP owns every connection, trigger and delivery. They meet at a single HTTP seam — /invoke — guarded by X-Gateway-Token. No channel/integration-specific code lives in CUGA.

┌─────────── CHANNELS (converse) ───────────┐ ┌─── INTEGRATIONS (watch / act) ───┐ Telegram · Discord · Slack · Web │ │ Box · GitHub · Gmail · Slack │ └──────────────┬────────────────────────────┘ └───────────────┬──────────────────┘ │ (AP piece triggers + send) │ (AP piece triggers) ▼ ▼ ╔══════════════════════════════ ACTIVEPIECES ══════════════════════════════╗ ║ inbound flow · schedule/poll flow · push flow (trigger → HTTP → send) ║ ║ holds all OAuth/secret CONNECTIONS · owns the OUTBOUND send step ║ ╚════════════════════════════════════╤═════════════════════════════════════╝ POST /invoke (X-Gateway-Token) ▲ answer ▼ │ ╔══════════════════════════════════ CUGA ═══════════════════════════════════╗ ║ Concierge (runtime ROUTER: list_capabilities · answer_now · find_or_create_flow · decline) ║ ║ CugaRuntime → per-agent CUGA graph + MCP tools Studio UI (/studio) ║ ║ Identity · Permissions · Credentials-connect UX · SubscriptionStore (sqlite) ║ ╚═══════════════════════════════════════════════════════════════════════════╝

Key design choices

  • Concierge = router, never a builder. It picks among pre-built agents; it never creates agents or writes code.
  • Flow assembly is deterministic code (ap_engine.py + flows.CHANNELS). The LLM only fills a few typed args — flows can't be hallucinated.
  • AP owns the outbound. Inbound replies and scheduled/poll results deliver via an AP send step to the caller's channel.
  • Worker = CUGA by default (CugaRuntime); react is opt-in.

The seam & ports (dev)

  • /invoke — every trigger calls back here; agent="concierge" routes to the router.
  • Activepieces :8081 · CUGA server :8100 · tool registry :8001.
  • AP → CUGA callback: http://host.containers.internal:8100/invoke.
  • Channel webhooks / OAuth callbacks need HTTPS → Cloudflare quick-tunnel (ephemeral).

2 The vocabulary (channels · integrations · triggers · agents)

Channels — converse on

Two-way chat surfaces. A message in → concierge → reply out.
Web, Telegram, Discord, Slack.

Integrations — watch / act on

Systems an agent watches or acts on.
Box, GitHub, Gmail, Slack (shared).

Triggers — how a run starts

NOW (ask now) · CRON (at a time) · POLL (every N, on change) · PUSH (an integration event).

Agents — the workers

Pre-built by a builder: skill (prompt) + tools (MCP) + channels + integrations + access. The concierge routes among them.

Direct-channel delivery — how a scheduled flow reaches a channel that lives outside AP

A flow has three legs — trigger · agent · delivery — and each can be AP-backed or direct. AP-backed channels (Telegram/Discord) get an AP send-step appended to the flow. A direct channel (Slack) has no AP connection, so:

  • Trigger stays in AP (the schedule piece is just a clock) → it POSTs to /invoke with deliver:true and source={type:channel, name:slack, thread_id:gw:slack:<chan>}.
  • Delivery is CUGA-side: /invoke sees a direct-channel sink and sends the answer itself via delivery.send_direct → slack_direct. No AP send-step.

One knob decides the split: delivery.channel_backend(ch) → direct|ap (override with EVENTS_<CH>_BACKEND). This closed the gap where a cron/poll delivering to direct-Slack would previously try an AP send-step and fail. Live (unit + app-level tests: delivery routing, no-AP-send-step, direct send)

The AP bug (kept for later): under AP 0.82 + slack-piece 0.17.2 the new-message APP_WEBHOOK trigger emits [] even for a clean channel_type:"channel" event — Slack events reach AP (EXECUTE_WEBHOOK jobs run) but no flow-run fires. 9 Credential story

How it works

  • CUGA hosts the connect UX for every connector (token paste or OAuth consent).
  • AP holds the token — CUGA passes the credential to AP as a connection; AP executes with it.
  • Grain follows credentials: shared (builder connects once, tenant-wide) vs per-user (each user logs into their own account → per-user flow).
  • Just-in-time: if an agent needs a per-user integration you haven't connected, the concierge replies CONNECT NEEDED with a link.

State

  • Live Telegram bot-token connection (secret) → used by the inbound + delivery flows.
  • Wired OAuth connect (Gmail/Box/Slack) — AP requires the OAuth code-exchange flow (it will NOT accept a pasted access/dev token); needs client id/secret + consent. ensure_oauth_connection fixed to AP's code schema (2026-07-05).
  • Wired Admin → OAuth-apps panel (enter client id/secret in UI vs .env).
  • Roadmap secrets vault (replace .env) for cloud.

10 NL → Flow validation the strategic piece

Turning a fuzzy utterance into the right flow — right agent, mode, cadence, delivery, or a safe decline — is the real product surface. Flow assembly is deterministic code; the only fuzziness is the LLM's argument selection for find_or_create_flow(agent, kind, cadence, source, deliver).

Today

  • Live path = LLM router (picks agent + mode + params).
  • Preview/no-LLM = deterministic regex classifier.
  • ⚠️ The two can disagree → preview ≠ live.
  • ⚠️ No pre-arm validation of the chosen args.
  • ⚠️ No labeled eval set → correctness is spot-checked, not measured.

Target (Run / MVP)

  • Dedicated Flow-Planner agent — typed FlowSpec output (mode·agent·cadence·source·sink).
  • One decide()→FlowSpec: dry-run returns exactly what live arms (preview==live).
  • Validation gate: valid cron, sane interval floor, agent exists+capable, delivery connected, dedup — before touching AP.
  • Benchmark harness: ~40 labeled utterances (incl. adversarial) → expected FlowSpec, scored per-field in CI; LLM vs regex baseline.
  • Model selection: bake-off on the corpus (accuracy / latency / cost) — the planner is latency-sensitive & correctness-critical.
  • Pattern: LLM proposes · validator gates · deterministic is fallback+baseline.

11 Deployment: local · cloud · tenant · user

Two independent axes — don't conflate them

Axis 1 — WHERE it runs: laptop (dev) · a cloud VM/container (prod) · managed platform.   Axis 2 — HOW MANY customers: single-tenant (Model A) · multi-tenant (Model B).

"Local vs cloud" is Axis 1; "Model A vs B" is Axis 2. Moving off the laptop to the cloud does NOT mean multi-tenant. A Model-A deployment is single-tenant but runs in the cloud with a real domain — one dedicated customer.

Tenant ≠ user — the hierarchy that resolves the confusion

Tenant = the customer / org (e.g. BofA), one per Model-A deployment. Users = the people inside that org (many). So single-tenant = one org = MANY users, not one user.

LayerWho / whatOwnsScoping
Tenantthe customer org (BofA)the deployment; the shared agents & integrationstenant/instance — agents are tenant-shared
Builder / admina role a user holdscreates agents; connects shared integrations (company Slack bot, shared Box); sets who can use whata user with the builder/admin role
Useran employeetheir own conversations/memory; connects per-user integrations (their Gmail); gated by per-agent permissionstenant/instance/user — run-state is per-user

Credential ownership is what makes one deployment serve many users: shared (builder connects once, tenant-wide — the company Slack/Box) vs per-user (each employee logs into their own account — "summarize my Gmail"). The bot token is always shared (one bot per org); the author of each message is what tells Alice from Bob. That author id maps to a tenant user via account-linking (decision 0007), so the right memory + per-user credentials + permissions apply. Author-id wired — every inbound message now carries source.user: Telegram (chat.id) and Slack (ev.user) — live-verified; Discord (author id via the AP flow) — wired, pending a live field-name check. Memory is per-thread (Slack thread_ts; Discord channel_id).

Model B (multi-tenant) = many orgs on one deployment (needs AP Enterprise multi-project + hard isolation) — NOT "many users". Model A already has many users.

Model-A cloud deployment (where we're headed) — mostly infra, not code

Promote the same stack from laptop + tunnel (dev) to one single-tenant cloud deployment (prod). Co-locate everything (they call each other constantly — never split AP-cloud / CUGA-local):

┌─────────────────────── one VPC / host (single tenant) ───────────────────────┐ │ │ │ real domain + TLS ─▶ CUGA server (:8100, EVENTS_ENABLED) │ │ (replaces the tunnel) │ ▲ │ │ ▼ │ /invoke │ │ Activepieces (CE, 1 project) ──▶ postgres + redis │ │ │ │ │ registry + MCP servers (cuga-*) │ │ │ │ secrets: vault/env (not .env) · state: managed DB + volumes │ └──────────────────────────────────────────────────────────────────────────────┘ inbound channels (Telegram/Slack Events) need the real domain · Box direct poll needs none

Changes: tunnel → real domain+TLS · .env → secrets manager · sqlite → managed DB + volumes · add a process manager/orchestrator. Unchanged: AP Community Edition, the scopes, the agents, the direct backends, the code.

13 Phase 3 & 4 — the roadmap

Phase 3 — full coverage + NL→flow rigor

  • Discord + Slack inbound round-trips (verify descriptors live).
  • PUSH live: GitHub PR watcher → Box resume watcher → Gmail.
  • OAuth per-user connect, live (Gmail).
  • Integration delivery (email/Gmail sink) — "send me… to my gmail".
  • POLL stored last-value state (robust on-change).
  • NL→flow: FlowSpec + validation gate + golden eval harness.
  • Benchmarking: NL→flow accuracy + answer quality.

Phase 4 — cloud & scale

  • Multi-tenant isolation (hard per-tenant AP projects + row-level).
  • OIDC/IdP identity; real per-user + channel account-linking at scale.
  • Managed AP + HA pg/redis; stable public URLs (no quick-tunnels).
  • Secrets vault (retire .env).
  • Shared state across replicas; horizontal scale.
  • Observability: tracing, metrics, NL→flow accuracy dashboards, alerting.
