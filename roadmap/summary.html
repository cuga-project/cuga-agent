CUGA Event-Driven Agents

What this is, how it's built, and what works

A technical overview · opt-in behind EVENTS_ENABLED · deeper detail in capabilities · use cases · board

CUGA today is a request/response agent — you open it, ask, and it answers. This layer makes it event-driven: agents that watch inboxes, files and repositories, run on a schedule, hold two-way conversations on chat channels, and deliver answers back on their own. It does this without rebuilding CUGA's reasoning — it reuses the existing agent graph, memory, config store and secrets, adds a thin set of endpoints, and delegates all the connection / OAuth / scheduling machinery to Activepieces (AP).

The whole layer is opt-in. With EVENTS_ENABLED off (the default), CUGA behaves byte-for-byte as it does today — no new routes, no new tables, no behavior change. With it on, the events endpoints mount and a background router starts. That's the contract that makes it safe to merge: it's additive, never a rewrite.

How it works

A builder defines an agent — a prompt/skill plus the tools (MCP servers) and the connectors it's allowed to use. End users talk to those agents from channels, and set up triggers in natural language ("summarize new resumes in Box", "every weekday 8am post the market brief"). A concierge router reads the request and does one of three things: answer immediately, arm a standing automation (a "flow"), or decline if nothing fits.

Setup is either plain English or a single /automate command whose router infers the trigger type from the phrasing — /automate summarize new emails arms a push flow, /automate the market brief every weekday 8am a scheduled one, /automate bitcoin every 5 min on a move a poll. It works the same from web chat and from any connected channel, so a user can stand up an automation without leaving Slack.

Every path — a chat message, a scheduled tick, a new-file event, an external webhook — is normalized onto a single internal endpoint, POST /invoke, which runs the right agent and returns or delivers the answer. Because each agent is a real CUGA agent_id and every request carries a thread_id, conversations keep context and each standing automation accrues its own memory. The reasoning engine isn't reinvented; it's wrapped.

The building blocks

The design rule is strict: don't duplicate CUGA, don't build an OAuth/connection framework — AP owns that. So the surface splits three ways. Almost everything is reused; a small, self-contained package is new; connections and the clock are delegated.

Reused from CUGA (unchanged)
  • The agent graph — reasoning, supervisor, sub-agents (DynamicAgentGraph).
  • Memory per thread_id; the config store of agent definitions.
  • Secrets (Fernet-encrypted) and the existing auth guards + chat UI.
New — the events package
  • The /invoke seam and the concierge router (answer / arm / decline).
  • The AgentRuntime port — one interface, so swapping the agent framework is one adapter (backends: cuga default, react, stub).
  • Direct channel backends (Slack, Discord) + a thin subscription index of armed flows.
Delegated to Activepieces
  • Connections & OAuth — tokens held and refreshed by AP.
  • Triggers & the clock — cron, poll, and app-event pieces (new email / PR / file).
  • Run history for standing flows.

Net-new footprint on core CUGA is essentially the events package plus two guarded lines in startup (route registration + a lifespan hook), both behind the flag. Two chat channels — Slack and Discord — bypass AP and run as direct backends, because AP's connector couldn't accept a pre-issued bot token and its message trigger returned empty payloads; direct is also instant instead of polled.

How a request flows

Two phases: a user arms an automation in natural language once; from then on it fires on its own.

The concierge is itself an agent; each worker is a distinct agent_id. A standing flow gets a stable per-subscription thread_id, so each automation carries its own context across firings.

The APIs added to CUGA

Two of these are the load-bearing seams; the rest let a builder define agents and let operators manage running automations from CUGA itself — without ever opening the Activepieces console.

EndpointPurpose
POST/invokeThe callback seam. Every trigger (channel / cron / poll / app-event / webhook) normalizes here; runs the agent, returns or delivers. Machine-to-machine, guarded by a gateway token.
POST/api/conciergeNatural-language entry: reuse or create a worker and arm a trigger. Supports a dry-run that builds the flow without publishing.
POST/api/events/agentsDefine an agent (prompt + tools + connectors); PUT …/agents/{name} to update, GET to list.
GET/api/events/subscriptionsThe armed automations, plus …/{id}/flow for the full source→agent→delivery view.
POST…/subscriptions/{id}/pause · resumeLifecycle control — CUGA drives Activepieces for you; DEL to remove.
GET/api/events/runsExecution log: every standing-flow run joined to its subscription and output; …/{id} for one run.
GET/api/events/connect/{app}Start an integration connection; …/callback completes OAuth, …/token stores a token. AP holds the credential.
POST/api/events/slack/events · /hook/{name} · /box/pollThe direct inbound adapters — Slack Events API, generic webhooks, and the Box poller — that bypass AP.
POST/api/events/link/{channel}Account-linking: bind a chat identity to a profile so a shared bot tells users apart. (GET …/me for the current identity.)
GET/api/events/status · channels · integrations · mcp-serversRead-only Studio views — what's enabled, connected, and available.

Where it gets hard

The difficulty isn't running the agent — it's pinning down an ambiguous request and stitching several steps across systems. These are the requests that expose the open questions above:

  • Ambiguous target or cadence. "Keep an eye on my repo for problems" — which repo, which event, poll or push, what counts as a problem? The router has to ask, or guess wrong.
  • Branch + approval. "When a resume lands in Box, score it; if it passes, draft an interview invite and ask a recruiter to approve before it sends." — one sentence, but it needs file-content extraction, a conditional branch, a cross-app hop (Box → Gmail), and a durable pause-for-approval step.
  • Cross-system with a condition. "When an invoice email arrives, match it to a purchase order and post it to the ledger, but flag mismatches to me." — extract, look up an external record, then deliver conditionally to two different destinations.
  • Compound schedule + query + per-item action. "Every morning, if any PR is older than three days, nudge its author and send me a summary." — a scheduled trigger, a filtered query, an action per result, and a digest — a single utterance that unfolds into a multi-step flow.
  • Event + timed escalation. "When a high-severity issue is filed, post it to the on-call channel, and if nobody acknowledges within 15 minutes, escalate to me on Telegram." — an app event, then a timer that depends on whether a human responded, then a conditional second hop. The flow has to hold state and wait.
  • Batch a stream into a digest. "Instead of pinging me for every new PR, collect them through the day and send one summary at 6pm." — an event trigger whose results are accumulated over a window and released on a schedule. Two triggers, shared state between them.
  • Cross-source correlation. "Every Monday, compare last week's support emails against our docs and tell me which topics need new documentation." — a schedule that reads two different sources, correlates them, and reasons about the gap — not a lookup, a synthesis.
  • Enrich, score, then route differently. "When a new lead form comes in, enrich it with company info, score the fit, send hot leads straight to a rep, and queue the rest for nurture." — a webhook, an enrichment step, a branch on the score, and different delivery per branch.
  • Sequential, multi-person approvals. "When a contract over $50k lands in Box, pull the key terms, send them to legal, and only after legal signs off, notify finance." — content extraction, a branch on value, then approvals chained across two people in order before the final action.
  • Delayed, conditional follow-up. "When a customer emails asking for a demo, draft a reply, and if they haven't responded in three days, follow up once." — an event, an action, then a scheduled check that only fires if a later event did not happen — the flow has to remember and un-fire itself.

Each of these is achievable, but each stretches the natural-language-to-flow translation and, in some cases, a primitive that isn't fully proven yet (durable approvals, document-body extraction). They're exactly why hardening that translation is the next focus.

What works today

  • All four chat channels converse two-way, live.
  • GitHub, Box and Gmail are connected and firing; a new PR, file, or email triggers an agent that delivers a result.
  • All five trigger types fire and deliver — e.g. an hourly "top trending GitHub repos → Slack" flow runs today.
  • Automations are created in plain English or a single /automate command, and managed from one console (pause, resume, delete, and a run log) — operators never touch the Activepieces UI.
  • The whole thing is tested (61 offline checks) and non-breaking (opt-in, additive; two guarded lines touch core CUGA).
  • Swapping the underlying agent framework is one adapter, not a rewrite — the event plane never depends on CUGA internals directly.

What doesn't (yet)

  • Box passes the file's name, not its contents. An agent judging a document currently sees the filename and metadata; reading the body needs a download step added before the agent runs.
  • GitHub's write path needs the right token scope. Arming a PR trigger creates a repo webhook, which requires a PAT with explicit webhook permissions — the system now surfaces this as a clear instruction instead of a raw error.
  • Instance-level isolation is nominal. Tenancy works; the finer "instance" grain always collapses to a default today.
  • Outlook and a couple of internal cleanups (a duplicate flow-builder path that risks drift) are on the roadmap, not done.
One security item before any shared, external deployment: the internal /invoke seam trusts the identity its caller asserts, guarded by a shared gateway token. That's fine for the internal AP→CUGA path and local use, but a multi-tenant public deployment needs an upstream identity layer (signed claims / an IdP) in front. This is the single most important thing to harden, and it's documented, not hidden. A few operational edges (an ephemeral tunnel URL, short-lived dev tokens) will also bite a naïve deploy.

Open questions

The honest set of decisions still ahead — none blocking internal use, all worth resolving before a broader rollout.

  • Multi-tenant isolation. Tenancy works, but the "instance" grain is nominal today and /invoke trusts a caller-asserted identity behind a shared token. What's the target model for a shared, external deployment — an upstream identity provider, signed scope claims — and when do we commit to it?
  • The cost of depending on Activepieces. AP buys us connections, OAuth and the clock for free, but it carries real operational weight: an ephemeral tunnel URL that breaks OAuth redirects on restart, a piece-catalog sync that can fail on a network blip, dev tokens that expire in hours, and a hard requirement to run on Postgres. Is the answer to invest in a named tunnel + managed AP, or to reduce the dependency over time?
  • Human-in-the-loop approvals. Many of the most valuable workflows want a "reply yes to approve" step. It isn't yet confirmed that a standing flow can durably pause for approval and resume on a chat reply — is that a primitive we need to build?
  • Hardening natural-language → flow. Turning a sentence into a correct automation has two fuzzy seams: understanding what the user meant (which agent, which trigger), and mapping a trigger's raw event payload into exactly what the agent needs to read. Both work for the common cases today, but both need hardening — schema- or model-derived field maps at setup time, and better disambiguation when a request is vague. This is the priority next step; a raw-payload safety net is already in place as a stopgap.
  • Every integration has a real-world cost. Adding a "piece" isn't just wiring code — each needs real credentials, the right OAuth scopes, sometimes a paid connector, and a live account to prove it actually fires. A piece that looks supported on paper can still be hours of credential setup away from working.
  • Testing this is genuinely hard, and needs a dedicated effort. The offline suite is green, but proving a live path means real accounts, an ephemeral public URL, tokens that expire in hours, and events you have to manually cause — send the email, open the PR, upload the file. Keeping this honest over time needs stable test accounts and a purpose-built end-to-end harness, not ad-hoc checks.
