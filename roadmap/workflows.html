0 The lightweight-app model

Today a cuga-app bundles a UI, its own tools, an orchestration loop, a scheduler, and delivery code. On the event-driven runtime, all of that except the tools is already provided. A "cuga app" collapses to two tiny files.

The app = a bag of tools

  • An MCP tool server — a handful of functions, often thin HTTP GETs (get_repo_stars, get_usage_stats, extract_doc).
  • A seed manifest — a few AgentSpecs wiring those tools to a trigger + channel.
  • No UI, no scheduler, no delivery code, no orchestration loop. The runtime owns all of it.

The runtime owns everything else

  • Triggers — NOW / CRON / POLL / PUSH, via Activepieces.
  • Channels — web, Telegram, Slack, Discord (converse + approve).
  • Integrations — Box, Gmail, GitHub, webhooks (watch + act; AP holds the creds).
  • Concierge — routes users to the right pre-built agent; branches and human-in-the-loop live in the agent's reasoning, not app code.
The one wrinkle for tracking: analytics needs history to say "stars gained this week." In most cases the source already keeps it — GitHub returns the live count; the usage-collector already exposes daily/monthly JSON — so the tool just fetches a snapshot/series and the agent reasons over it. No new state in the app.
How you create any of these — one command. Besides plain English, /automate <what> is one slash command whose router picks the trigger mode — push / cron / poll — from the phrasing, so you never pick a mode. It works from any surface (web Studio chat and channels like Slack/Telegram/Discord — all call concierge.run): /automate summarize new emails and message me → PUSH (gmail) · /automate the market brief every weekday at 8am → CRON · /automate check bitcoin every 5 min on a move → POLL. Five hidden overrides force a mode (/watch = /automate, /push, /schedule, /cron, /poll); manage the results in the Flows console (make flows).

1 The three primitives every idea composes

Triggers · 4 modes

  • NOW ask → answer
  • CRON scheduled (e.g. nightly)
  • POLL check every N, emit-on-change
  • PUSH native app event fires

Channels · converse & approve

  • web Telegram Slack Discord
  • A channel message is the approval UI — "reply yes/no" is the whole approval system.

Integrations · watch & act

  • Box Gmail GitHub webhooks
  • Trigger in system A, act in system B — pure config, since targets are just connectors.

9 Two concrete specs — the whole "app" is ~30 lines

The star tracker and nightly usage analytics you asked for. One tiny tool server plus two AgentSpecs in seed.py — no new heavyweight app.

# tool server "cuga-stats" — the entire "app"
get_repo_stars(repo)        # GET api.github.com/repos/{repo} -> stargazers_count, forks, watchers
get_usage_stats(window)     # GET usage-collector .../export.json?window=7d&token=...

# seeded agents (in seed.py) — the entire "config"
AgentSpec(
  name="star_tracker",
  prompt="Track cuga-agent stars. Report today's count, delta vs yesterday, 7-day trend, notable jumps.",
  mcp_servers=["cuga-stats"],
  integrations=[{"app":"gmail","ownership":"per-user"}],
  trigger="CRON@21:00", channels=["web"], deliver="email")   # or POLL to ping Slack on a jump

AgentSpec(
  name="usage_analyst",
  prompt="Pull nightly usage. Summarize requests, unique visitors, top apps, error rate, "
         "provider-call spend, and the 3 most common utterance themes. Flag anomalies vs the 7-day baseline.",
  mcp_servers=["cuga-stats"],
  integrations=[{"app":"gmail","ownership":"per-user"}],
  trigger="CRON@21:00", deliver="email")
The usage-collector already keeps history (daily/monthly JSON + CSV export), so usage_analyst needs no store at all — it reads the series the collector produces and narrates the deltas.

The reusable primitives

  • Branch ⎇ — the agent picks a path from enriched data; no if/else app code.
  • Human-in-the-loop ✋ — a channel message is the approval UI.
  • Cross-integration hop — trigger in A, act in B; targets are just connectors.
  • Trigger mode is a free axis — one app becomes NOW + CRON + POLL + PUSH variants with zero new tools.

The payoff

  • One tool bag powers many agents: cuga-finance → Market Brief + Price Alert; cuga-code → PR Reviewer + Triager + Release Notes + Standup + DORA + Security.
  • Tracking any number is a config change, not an app.
  • Enterprise versions differ only in which GET (billing/CRM/warehouse) and which channel.
  • The richest demos — Release Captain, On-Call Router, Onboarding Runner — chain 4–5 steps across 3 systems with an approval gate. That's a workflow engine, not a chatbot.
