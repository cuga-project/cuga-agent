1 What it is (and isn't)

The events layer turns CUGA from a request/response agent into an event-driven one: agents that watch inboxes, folders and repos, run on a schedule, converse on chat channels, and deliver answers back — without rebuilding CUGA's reasoning. It reuses CUGA's agent graph, config store, memory, and secrets; it adds two endpoints and a concierge; it delegates connections, OAuth, triggers and the clock to Activepieces.

The opt-in contract

  • Everything is gated by EVENTS_ENABLED (default off).
  • Flag off → vanilla CUGA, byte-for-byte: no routes mounted, no lifespan additions, no new tables. The import is try/except-wrapped so a missing dep can't block boot.
  • Flag on → two endpoints mount, the concierge + AP client start, one extra DB (EVENTS_DB) opens.
  • Net touch on core CUGA: two guarded lines in main.py (route registration + lifespan). Nothing existing changes behavior.

What it deliberately does NOT own

  • OAuth / connections — Activepieces holds & refreshes tokens. CUGA has no connection framework by design.
  • The clock & integration triggers — AP's cron/poll/piece triggers fire and call back.
  • A new memory or multi-agent store — it uses CUGA's agent_configs + thread memory as-is.
  • It is not a no-code app builder: the concierge routes to pre-built agents, it never invents tools or agents.

2 The model in one breath

A builder defines agents (a skill/prompt + MCP tools + the connectors it may use). End users chat from channels and set up triggers in natural language. A concierge router decides: answer now, arm a standing flow (cron / poll / push), or decline. Every path converges on one HTTP seam.

The concierge is itself an agent; each worker is a distinct agent_id. The envelope carries thread_id end-to-end, so follow-ups keep context and every standing trigger accrues its own per-subscription memory. No parallel memory is invented.

7 The AgentRuntime port — framework-swap in one adapter

Only two legs bind to an agent framework: defining an agent and running it. Both sit behind one interface, so swapping the worker framework is writing one adapter, not a rewrite. AP and /invoke never mention CUGA.

class AgentRuntime:            # runtime.py — the port
    upsert_agent(spec)   -> agent_id
    get_agent(agent_id)  -> spec | None
    list_agents()        -> [spec]
    run(agent_id, thread_id, text, *, deliver?) -> answer   # memory keyed by thread_id

Honest note on multi-agent: CUGA's own /stream still hardcodes cuga-default. Multi-agent execution is confined to the new /invoke path, which builds a graph per-agent — so it's additive and non-breaking, not a change to core CUGA's request runtime.

8 Isolation & identity

Two grains

  • scope = tenant/instance/user (per-user) — namespaces threads/memory, subscriptions, and AP connection externalIds (ea::<tenant>::<user>::<app>).
  • agent_scope = tenant/instance (per-tenant) — agent definitions are shared; each user runs them in their own memory namespace.

Shared bot, distinct users

  • Every message carries its author (source.user = Slack/Discord id).
  • An account-linking handshake (/link <token>) binds a channel id to a profile.
  • Per-user integrations require each user to OAuth with their own account.

Honest limitations here

  • GAP instance_id is effectively always default — instance-level isolation is nominal today.
  • RISK /invoke trusts a caller-asserted scope behind the gateway token (it's the internal AP→CUGA seam). Real multi-tenant isolation needs an upstream auth layer / signed scope claims — the #1 item to fix before a shared deploy.

11 Security posture — before you expose it

What's guarded, what isn't, and the assumption. Fine for local dev; read this before exposing beyond localhost.

RISK The seam trusts caller scope

/invoke becomes whatever Principal the caller names, guarded only by the gateway token. By design (internal seam), but real isolation depends on an upstream auth layer + a secret token. Signed scope claims / an IdP is the hardening path.

GAP Open by default if unset

  • Empty GATEWAY_TOKEN → /invoke + poll/webhook endpoints are unauthenticated (warns loudly at startup).
  • Webhook key gate enforced only if EVENTS_WEBHOOK_KEY set (constant-time compare).
  • Slack signature verification on only if SLACK_SIGNING_SECRET set.
  • _is_admin returns True when there's no user store (dev convenience) — production must run with the user store on.

GAP OAuth state is unsigned

base64-JSON, trusted on callback — a crafted state could steer a connection's externalId. Sign/nonce before public OAuth. Tracked, not yet fixed. Closed this PR: envelope validation now runs on every /invoke (malformed → 400).

12 Operational sharp edges

The recurring warts — worth knowing so a green flow that "does nothing" doesn't puzzle you.

Environment & tunnels

  • The quick-tunnel URL is ephemeral — every cloudflared restart invalidates the public URL, Slack Events URL, OAuth redirects, and AP frontend URL. A named tunnel ends this. (Direct Discord + Box poll are outbound-only, so they don't care.)
  • The server caches .env at startup — restart after any change.

Credentials & AP

  • Do NOT set AP_WORKER_TOKEN — AP 0.82 mints it as a JWT; a random value crash-loops the worker.
  • Box dev tokens expire ~60 min; Gmail (Testing) refresh tokens expire after 7 days — re-Connect weekly.
  • Run AP Community Edition on Postgres (the sqlite build wipes its own project).
  • Fresh AP must sync its piece catalog from cloud; a network blip → piece_metadata_not_found 404s. Fix: make ap-pieces (idempotent). make doctor reports piece status.

13 Bottom line

What's genuinely true today

  • 4 channels + 3 integrations + a generic webhook, all 5 trigger shapes, wired end-to-end and covered by 61 offline tests.
  • GitHub & Box proven against real APIs; Slack/Discord/Telegram/web live; NL and /automate both create real AP flows you manage from CUGA (pause/resume/delete, run log).
  • Near-zero blast radius: opt-in, additive, non-breaking. Framework swap = one adapter.

What to be honest about

  • Gmail fire and Box content are the two unproven/partial legs; GitHub write-path needs the right PAT scope.
  • /invoke trusting caller scope is the #1 thing to harden before a shared multi-tenant deploy.
  • Instance isolation is nominal; two flow-builders risk drift; Outlook is unbuilt.
  • The tunnel/AP operational edges are real and will bite a naïve deploy.
