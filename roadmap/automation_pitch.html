CUGA · Product direction

From a chat agent toward automation — the direction, and an honest read of where we are

CUGA reasons well, but only when asked. We've built an event-driven layer that lets it act on its own — on a schedule, on an event, across a few apps. We think there's a credible path from there to real, multi-step automation. This lays out the direction, what's actually built, and what's still a bet.

The middle stage works today, opt-in and non-breaking. The right stage is a direction we've validated on paper and started building — not something that runs end-to-end yet.

The thesis we're testing

Most automations share a shape: something happens → decide what to do → do it across your tools. The deciding is the hard part, and it's what an LLM is good at. So we let a mature platform own the plumbing and let CUGA own the judgment.
Activepieces = the plumbing
  • connectors, OAuth, tokens
  • triggers & the clock
  • sends & actions, run history
CUGA = the judgment
  • turn a request into a flow (NL → flow)
  • reason inside each step
  • read, judge, compose, route

If this holds, the differentiator is the translation — plain English into a correct, running flow — plus the reasoning inside it. That's the part we're betting we do better than a pure automation tool. It's also the part that's hardest and least proven.

Why the position is worth taking

Agents don't plumb

Agent frameworks reason well but have no OAuth, no triggers, no large connector catalog. Reusing a platform for that is cheaper than rebuilding it.

Platforms don't reason

Zapier / n8n / AP have the plumbing but no brain — you hand-build every branch and field-map. That's the friction an LLM can remove.

The seam we're aiming at is NL → flow. You say “when a resume lands in Box, match it to the JD and route strong fits to hiring.” Today we can arm the simple half of that; the branch, the file content, and the routing are exactly what we're building. Whether we can make that translation reliable is the open question the whole bet rests on.

What's actually built (with the caveats)

opt-in & non-breaking4 channels live Box · Gmail · GitHub5 trigger types fire NL + /automate arm real flows61 offline tests

The event plane sits behind a flag; off, CUGA is unchanged. On, it arms real Activepieces flows and delivers to real accounts. But grounded: it's proven mostly single-operator; Gmail's fire path is lightly exercised; Box passes a file's name, not its contents; and it is not multi-tenant-secure for a shared external deploy yet. Real, but early.

The path — three horizons

H1 · Foundation
Built
trigger × agent × deliver. Immediate answers, schedules, app-event watchers; four channels; Box / Gmail / GitHub; per-user credentials; managed from CUGA. This is the part that works today.
H2 · Real automation
In progress
Five primitives, mostly not built yet: durable state · branch & multi-step · file content · source reads · approvals. Each is scoped; the live engine only builds linear flows today, so this is genuine engineering, not config. This is where the enterprise use-cases live.
H3 · Platform
Later
Breadth & hardening: the connector long tail (each a real credential/OAuth effort), NL→flow disambiguation + validated field maps, multi-tenant identity, and a lightweight app-authoring model.

A sanity check, not a proof

We ran all 420 official Activepieces templates through a heuristic that reads each one's trigger and pieces and asks what our stack would need to build it. Treat these as estimates of shape, not shipped builds:

278
lean on AI — the part CUGA is suited for
307
would need the multi-step / branch builder (H2)
382
use an app we'd have to add — a long connector tail

Read carefully, this is encouraging but sobering: the logic looks reachable, but the dominant cost is connectors — a long tail, each with real setup — and the numbers say nothing about whether NL→flow translates any given template correctly. It tells us the direction is plausible, not that it's done.

What we're not claiming

The hard primitives aren't built — and some are unproven

Durable state, branching in the live engine, and a pause-for-approval gate are scoped but not shipped; whether a flow can durably pause and resume on a chat reply isn't yet confirmed.

NL → flow is reliable only for simple cases

Vague requests, ambiguous cadence, and mapping each trigger's payload correctly are open problems. Hardening this is the bet; it isn't finished.

Every connector is real work

The 382-app tail isn't a switch — each needs credentials, scopes, and a live account to prove it fires. This is a sustained effort, added per real demand, not up front.

Not ready for a shared, external deployment

/invoke trusts a caller-asserted identity behind a shared token; multi-tenant use needs an upstream identity layer first. Fine internally; a gate before going wider.

The honest one-liner

CUGA's edge is reasoning. Event-driven CUGA lets that reasoning act instead of wait — that part is real. Turning it into dependable, multi-step automation is a credible next step we've started and validated on paper, but it rests on primitives we haven't finished and a translation problem we haven't fully solved.
