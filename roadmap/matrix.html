0 How to read it

C = CUGA does it A = Activepieces does it trigger/inbound · reason · deliver — the three legs of a run — = not applicable

Reasoning is always CUGA (the worker agent answers; the concierge does NL→flow). So the middle leg (reason) is C in every live cell — the split is about who handles the trigger and the delivery. For CRON/POLL/PUSH the connector column is the delivery sink (a channel) or the watched source (an integration).

1 Why Activepieces — and why Slack/Discord go direct

What Activepieces brings to the table

AP is the connectivity fabric — the boring, hard, never-want-to-build-yourself plumbing between an agent and the outside world:

  • OAuth token lifecycle — obtains, stores, and refreshes per-user OAuth tokens (Gmail, Box). This is the genuinely hard part: you never touch a refresh token.
  • Integration triggers (the sentry) — AP sits on Box / GitHub / Gmail (a webhook or a poll) and fires /invoke when something happens. You don't run that watch loop.
  • The clock — CRON / POLL fire from AP's schedule piece (a durable timer).
  • 100s of pre-built connectors — Notion, Jira, Salesforce, Calendar, Drive, Slack, Telegram… the long tail you'd otherwise hand-build one API client at a time.
  • Run history & retries — every flow run is visible + retryable in AP's console.

In one line: AP holds the credentials and watches the world; CUGA does the thinking. AP is worth most where an integration needs OAuth refresh or is part of the long tail.

Why Slack & Discord skip AP (go direct)

A chat bot is the one case where AP adds cost, not value: the vendor API already takes the bot token directly, so AP's OAuth machinery is dead weight — and its channel pieces actively hurt us:

  • Slack — AP's new-message trigger emitted [] (a real AP 0.82 + slack-piece bug), and AP's OAuth2 connection refuses a pre-obtained bot token. Slack's own Events API takes the xoxb token → instant, no OAuth wall.
  • Discord — AP polls (~5 min latency, no push). Discord's Gateway (a WebSocket) is instant and needs no public URL (it's an outbound connection).
  • The rule: a token-auth channel with a simple vendor API → direct (instant, fewer moving parts, no OAuth refresh needed). An OAuth-watched integration → AP.

Direct isn't "dropping AP" — it's using AP only where it earns its keep. Telegram is still on AP (its webhook + send are fine); it could go direct too.

3 Worked flows — how a cell becomes a run

Each step is tagged C (CUGA) or A (Activepieces). Notice the handoff: AP (or a direct adapter) gets the event to /invoke → CUGA reasons → AP or a direct adapter delivers.

★ Hero: the résumé watcher — armed from Slack, watched on Box, delivered to Slack

"When a résumé lands in my Box, judge it against the JD and post the verdict here." — one flow that shows both halves: AP watching an integration, CUGA conversing + reasoning + delivering direct.

Phase A — arming (you set it up by talking to the bot):

  1. C You type it in Slack → Slack's Events API hits CUGA's /api/events/slack/events (direct, no AP).
  2. C The concierge runs: reads it as a PUSH, picks resume_judge, sets the sink = this Slack channel.
  3. A The concierge calls create_push_flow → AP builds a flow that watches your Box folder (new_file trigger, using your Box OAuth connection). AP now sits on Box.
  4. C CUGA records the Subscription in its DB and replies in-thread: "Armed."

Phase B — firing (a résumé actually lands):

  1. A A PDF drops in the folder → AP's Box trigger fires → POST /invoke(resume_judge) with the file reference.
  2. C CUGA's resume_judge worker reads the JD + file and scores fit → "MATCH / SKIP + why."
  3. C The verdict posts to Slack directly (chat.postMessage, in the thread) — no AP send-step.

Who did what: A held the Box OAuth token + watched the folder (steps 3, 5); C conversed, reasoned, and delivered (1, 2, 4, 6, 7). That's the division in a single flow.

One flow per trigger mode

NOW ask, get an answer

"What's the capital of France?" in Slack.

  1. C Slack Events → /invoke (direct).
  2. C concierge → geobot answers.
  3. C chat.postMessage reply, in-thread.

No AP at all — a direct channel end to end.

CRON on a clock

"Every weekday at 8am post a market brief to Slack."

  1. C Slack → concierge arms it → A create_schedule_flow (AP schedule, 0 8 * * 1-5).
  2. A AP's clock fires at 8am → /invoke(market_briefer).
  3. C worker writes the brief → C Slack direct delivery.

AP = the alarm clock; CUGA = brain + delivery.

POLL watch, speak on change

"Watch bitcoin every 2 min and ping me on any move."

  1. A AP clock every 2 min → /invoke(pricebot, emit-on-change).
  2. C worker pulls the price (cuga-finance) + decides "changed?" (prompt-only — no stored last-value*).
  3. C if it moved → Slack direct ping; else silence.

Same clock as CRON + a CUGA diff. *the weak spot.

PUSH react to an event

"When a PR opens on my repo, summarize it and post to Discord."

  1. C concierge arms it → A create_push_flow (AP watches the repo via a GitHub webhook + your PAT).
  2. A a PR opens → AP fires → /invoke(summarizer).
  3. C worker summarizes → C Discord direct (Gateway REST).

AP watches GitHub; CUGA reasons + delivers direct. (The résumé watcher above is the Box version.)

4 Role summary — what each side owns

C CUGA always owns

  • Reasoning — the worker agent answers (every cell's middle leg).
  • NL → flow — the concierge decides trigger/agent/cadence/sink (plain English or the /automate <what> slash command, whose router picks push/cron/poll from the phrasing — same concierge.run from any surface).
  • Direct channels — Slack (Events API) & Discord (Gateway): inbound + delivery, no AP.
  • Web — in-process.
  • Identity, memory, permissions — per-user, per-thread.

A Activepieces owns

  • The clock — CRON/POLL fire from AP's schedule piece.
  • Telegram — inbound webhook + send.
  • Integration PUSH — watches Box / GitHub / Gmail (webhook/poll) and fires /invoke.
  • OAuth token lifecycle — holds + refreshes per-user tokens (Gmail, Box).
  • The long tail — 100s of connectors for the Sprint/Fly phases.

Every live cell is a handoff: AP (or a direct adapter) gets the event to /invoke → CUGA reasons → AP or a direct adapter delivers. CUGA is the brain; AP is the connectivity fabric for everything not taken direct.

The line we're drawing: channels → direct (Slack/Discord done; Telegram could follow) · integrations → AP (Box now back on AP, alongside GitHub/Gmail) · the clock → AP for now (a CUGA scheduler would retire it). AP's durable value is OAuth + the long-tail connectors; everything else is replaceable.
