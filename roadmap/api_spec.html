Auth model — four gates who's allowed to call what

Every endpoint sits behind one of four gates. This is the first thing to know about any call:

GateHeader / paramGuards
Gateway tokenX-Gateway-Token: <GATEWAY_TOKEN>Machine-to-machine seams: /invoke, /box/poll. AP and internal adapters carry it. Empty token ⇒ open (warns).
Provider signatureX-Slack-Signature · ?key=Slack Events (HMAC over the signing secret); the generic webhook's optional shared ?key.
Principal (headers)identity headers → scopeUser-facing reads/writes. Resolves tenant/instance/user; every list is isolated to that scope. ⚠ caller-asserted today (roadmap: IdP).
Admin / Builderrole on the principalAgent create/update (builder); users, channel-arm, OAuth-apps (admin). No user store ⇒ open (dev).

The envelope the one shape every trigger arrives with at /invoke

Everything funnels through POST /invoke as this normalized envelope. Learn it once; it explains every trigger.

{
  "agent":  "mailbot",              // target worker agent_id, or "concierge" to route
  "text":   "summarize each new email and post it here",   // the prompt / utterance
  "deliver": true,                  // true = CUGA delivers the answer itself (direct channel)
  "scope":  "acme/default/alice",   // the principal (tenant/instance/user) the run executes as
  "source": { "type": "integration",          // channel | integration | time
              "name": "gmail",                 // slack | gmail | box | github | cron | …
              "thread_id": "acme/default/alice::gw:slack:C123",  // memory key + return address
              "user": "U_ALICE" },             // channel-native AUTHOR id (per-user identity)
  "event":  { "kind": "new_email",             // message|new_email|new_pr|new_issue|new_file|tick|runonce
              "payload": { "subject":"…", "from":"…", "body":"…", "_raw": {…} } },
  "trace_id": "tr_ab12"             // optional; generated if absent
}

1 · The load-bearing seams

POST /invoke

The single callback seam. Every trigger normalizes here; runs the agent and returns or delivers the answer.
Called by
AP flows (their HTTP step) · the direct adapters (Slack/Discord/Box/webhook handlers loop back to it) — never a browser.
When
Every trigger fires: a cron tick, a push event (new email/PR/file), a channel message, a poll, a webhook.
Auth
Gateway token
Routing
agent=="concierge" → the NL router; a concrete agent → runs that worker. Delivers when deliver=true and the thread_id names a direct channel.
In — a Gmail push firing
{ "agent":"mailbot", "deliver":true,
  "scope":"acme/default/alice",
  "text":"summarize each new email",
  "source":{"type":"integration","name":"gmail",
    "thread_id":"…::gw:slack:C123"},
  "event":{"kind":"new_email","payload":{
    "subject":"Q3 board deck",
    "from":"cfo@acme.com","body":"…"}} }
Out
{ "ok":true, "agent":"mailbot",
  "answer":"Q3 board deck from the CFO — …",
  "trace_id":"tr_ab12",
  "meta":{ "agent":"mailbot","backend":"cuga",
    "mcp":["cuga-finance"],"tools":["get_price"],
    "ms":4200 } }

Errors: 401 bad token · 400 invalid envelope · 404 unknown agent · 500 run failed. Special: a channel "/link <code>" message returns {ok,linked} (account binding).

POST /api/concierge ?dry_run=1

Natural-language entry — the web-chat door. Reuse-or-create a worker and arm a trigger, or answer now.
Called by
The web chat UI (and any programmatic NL client).
When
A user types NL or a /automate command in web chat. (Channel messages reach the concierge through /invoke instead.)
Auth
Principal (headers) — no gateway token.
In
{ "text":"every weekday 8am post the
           market brief to this channel",
  "thread_id":"web:local" }

// dry-run (no side effects):
//   POST /api/concierge?dry_run=1
Out — live vs dry-run
// live:
{ "ok":true,
  "reply":"ARMED cron for market_briefer → web…",
  "scope":"acme/default/alice","trace_id":"tr_x" }
// dry_run:
{ "ok":true,"dry_run":true,
  "decision":{"mode":"CRON","cadence":{…}}, … }

2 · Trigger adapters what fires /invoke, and who calls them

POST /api/events/slack/events

Slack Events API receiver (direct backend). Verifies the signature, acks in <3s, answers in the background.
Called by
Slack (Events API), on your app's Request URL.
When
Every message in a subscribed channel; plus a one-time url_verification handshake.
Auth
Slack signature
In — Slack posts
{ "type":"event_callback",
  "event":{ "type":"message",
    "text":"@cuga price of bitcoin?",
    "channel":"C123","user":"U_ALICE",
    "ts":"1699.5" } }
Out
{ "ok":true }
// (answer is posted back to the
//  thread out-of-band via chat.postMessage)
// url_verification → echoes challenge

Discord has no endpoint — it's a Gateway WebSocket background task (_discord_answer) that connects on boot and loops MESSAGE_CREATE → /invoke → reply. Same shape, no public URL.

POST /api/events/box/poll

Direct Box watcher (opt-in, EVENTS_BOX_BACKEND=direct). Polls a folder, fires the agent on each new file.
Called by
An AP schedule flow (schedule → this endpoint), or you, manually / from a test.
When
Each scheduled tick. Server tracks the per-folder watermark so only files added since the last poll fire.
Auth
Gateway token
In
{ "folder_id":"0", "agent":"resume_judge",
  "deliver_to":"slack", "deliver_target":"C123",
  "scope":"acme/default/alice",
  "since":"2026-07-08T06:00:00Z"  // optional; else server-tracked
}
Out
{ "ok":true, "folder":"0",
  "processed":[{"id":"f1","name":"resume.pdf"}],
  "newest":"2026-07-08T09:12:00Z",
  "trace_id":"tr_bp" }

Each new file is dispatched to /invoke with event.kind=new_file, payload {file_id,name} (filename only — the content gap).

POST /api/events/hook/{name}

Generic inbound webhook (direct, no AP). Any external system POSTs a payload; an agent triages it.
Called by
Any external system — CI, monitoring, a form, a payment provider.
When
Whenever that system fires. {name} is your label for the source.
Auth
?key (only if EVENTS_WEBHOOK_KEY is set)
In — query + any JSON body
POST /api/events/hook/ci-failed
  ?agent=incident_triage
  &deliver_to=slack&target=C_ONCALL&key=…
{ "repo":"acme/api","status":"failed",
  "run":"#4821" }
Out
{ "ok":true, "webhook":"ci-failed",
  "agent":"incident_triage",
  "answer":"CI failed on acme/api run #4821 — …",
  "delivered":true, "trace_id":"tr_hk" }

3 · Flow lifecycle manage armed automations from CUGA — never open the AP console

EndpointIn → OutCalled by / when
GET /api/events/subscriptions — → {scope, subscriptions:[{id,mode,target_agent,source_connector,deliver_to,flow_name,ap_flow_id,status,…}]} Studio / user — list my armed flows (scope-isolated).
POST …/subscriptions/{id}/pause — → {ok,id,status:"paused"} (also disables the AP flow) User — pause a flow.
POST …/{id}/resume — → {ok,id,status:"active"} User — resume.
DEL …/{id} — → {ok,id,deleted:true} (also deletes the AP flow) User — remove.
GET …/{id}/flow — → {ok, subscription:{…}, ap_flow:{trigger,steps…}} Studio — render the live flow read-only.
GET /api/events/runs — → {scope, runs:[{id,status,agent,mode,integration,channel,utterance,started_at,finished_at}]} Studio — the execution log (AP runs joined to subscriptions).
GET /api/events/runs/{id} — → {ok, run:{…}, answer, trigger_payload, error} Studio — one run's detail + the agent's output.
GET /api/events/flows/console — → HTML page A self-contained flows console (no build step).

5 · Connections & OAuth CUGA hosts the login; AP holds the token

EndpointIn → OutCalled by / when
GET /api/events/connect/{app} ?scope&agent&ownership → 302 to the provider's consent (OAuth), or {ok,kind:"token",message} (PAT apps) The user — via a link the concierge relays ("connect your gmail: …").
GET …/connect/{app}/callback ?code&state → HTML "✅ connected" (or 302 back). Hands AP the code; AP does the token exchange. The OAuth provider redirects here after consent.
POST …/connect/{app}/token {token,ownership?} → {ok,app,connection}. Token-auth apps only (GitHub/Telegram/Discord); OAuth apps get a 400. The user — pastes a PAT/bot token in the Studio.
GET /api/events/connections — → {scope, connections:[{id,externalId}]} Studio — which integrations I've connected.

The two phases, in endpoints

To tie it together — a standing automation touches these APIs in order:

ARM (once):  user → POST /api/concierge  (or a channel msg → /invoke → concierge)
                  → concierge builds the AP flow  → confirms "armed"
             (first-time per-user integration → GET /connect/{app} → …/callback)

FIRE (every event):  AP trigger / adapter → POST /invoke → run agent → deliver
MANAGE:  GET /subscriptions · /runs · POST …/pause|resume · DEL …/{id}
